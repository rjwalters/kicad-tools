# Evaluation: tscircuit as an upstream producer and a peer autorouter

**Date**: 2026-09-30
**Upstream**: https://github.com/tscircuit (organization; many small repos)
**Upstream license**: MIT for every repo examined below, except
`dataset-srj18`, which commits no LICENSE file
**Registry entries**: `tscircuit`, `tscircuit-autorouter`
(`kct ecosystem show <id>`)

## TL;DR

The registry used to file tscircuit under "reference / watch". The reason
was that it exported Gerbers, pick-and-place and BOM files directly and
shared no artifact with us. That is no longer true, and the entry's own
re-evaluation trigger ("first-class `.kicad_pcb` / `.kicad_sch` emission")
has fired:

- **tscircuit is now an upstream producer of KiCad projects.** The CLI's
  build step turns designs into KiCad files through `circuit-json-to-kicad`,
  and `kicad-to-circuit-json` converts in the other direction. It now has the
  same relation to us as atopile and SKiDL: **upstream / complementary**.
- **Its autorouter is a separate peer** that was never registered. It is
  MIT, under active development, uses a different algorithm family from
  ours, and publishes a benchmark derived from real KiCad boards. Registered
  as **peer / watch** until we measure it.

Nothing has been measured yet. The two follow-ups below do the measuring.

## What tscircuit is now

tscircuit describes circuits as TypeScript/React components
(`<board>`, `<resistor footprint="0402" …/>`). `@tscircuit/core` compiles
them to **Circuit JSON**, a flat list of typed elements
(`source_component`, `pcb_component`, `pcb_trace`, `schematic_trace`, …).
Every other tool in the organization is a converter into or out of that
format.

| Repo | Direction | Notes |
|---|---|---|
| `circuit-json-to-kicad` | Circuit JSON → `.kicad_sch` / `.kicad_pcb` / `.kicad_pro` / `.kicad_mod` / library | Staged converters. The PCB converter has stages for nets, footprints, **traces, vias, copper pours**, keepouts and graphics. Its tests run `kicad-cli` against the output. The LICENSE is MIT for code; some interop test artifacts were generated by KiCad and carry KiCad's licenses. |
| `kicad-to-circuit-json` | `.kicad_sch` / `.kicad_pcb` / `.kicad_mod` / `.kicad_sym` → Circuit JSON | Mirrors the pipeline above. Also handles legacy KiCad 5 footprints on a best-effort basis. |
| `kicadts` | read / edit / write | Typed model of KiCad's file format, one class per token, with deterministic formatting. Its tests round-trip the KiCad demo files. |
| `cli` (`tsci`) | build | `cli/build/generate-kicad-project.ts` and `build-kicad-pcm.ts`, so KiCad output is a first-class build target. |
| `jlcsearch` | parts | Constraint-based JLCPCB part search. Overlaps our parts/LCSC tooling in idea only. |

### What it means for us

- A tscircuit design can now reach our pipeline as a native KiCad project,
  so we need no format bridge. Given our mission (agent-driven PCB creation),
  a TypeScript front end that emits KiCad expands who can reach `kct route`
  and `kct check`.
- The quality of that output is **unknown**. Nobody has run a generated
  project through `kct check`, LVS and `kicad-cli pcb drc --refill-zones`,
  our two-engine bar for "manufacturable". Until someone does, treat
  tscircuit as a candidate front end, not a supported one.
- `kicadts` is the closest analogue to our file-handling layer in another
  language. Its round-trip fixtures are a cheap source of edge cases, and
  because it is MIT, ideas and test cases may move with attribution.

## The autorouter (`tscircuit-autorouter`)

Published as `@tscircuit/capacity-autorouter`. The README describes it as
"hundreds of algorithms organized in a Pipeline", using successive
approximation and hypergraphs rather than routing one net at a time
([blog post](https://blog.autorouting.com/p/hypergraph-autorouting)). That
is a different family from our A\* core and from KiCadRoutingTools, which is
itself a reason to measure it.

- **Input**: `SimpleRouteJson`. This is not a KiCad file. It is an abstract
  problem made of layer count, minimum trace width, rectangular obstacles,
  connections and bounds. `@tscircuit/core`'s
  `getSimpleRouteJsonFromCircuitJson` produces it, so a KiCad board reaches
  the router through `kicad-to-circuit-json` → Circuit JSON → SRJ.
  **Any comparison must check that this chain keeps clearances, netclasses
  and zones.** If the abstraction drops a constraint, a benchmark score is
  meaningless.
- **Post-route simplification** is a separate pipeline that takes routed
  traces and only cleans them up. That is comparable in scope to our own
  post-route optimization passes.
- **Bug-report workflow**: a failing route in the tscircuit web editor
  becomes a downloadable fixture and then a snapshot test. This is worth
  comparing with how we turn router failures into regression tests.

### Benchmark data

- `dataset-srj18`: 16 SRJ problems generated from **5 Arduino boards**
  (from `sabogalc/KiCad-Arduino-Boards`, WTFPL) and **11 Antmicro boards**
  (upstream repositories listed in the dataset's `source-files.json`).
  The dataset repo commits no LICENSE, so we **use the source `.kicad_pcb`
  files, not the dataset**. That is the same policy as
  `benchmarks/external/`, which fetches pinned boards at run time and never
  commits them. Check each Antmicro repo's license before pinning it.
- `autorouting-dataset-01`: 200 tscircuit-native problems (MIT). These are
  less useful to us because they are not KiCad boards.

## License position

Every code repo examined is MIT, so `license_compat = "mit-clean"`: code may
move with attribution. In practice we don't expect to move code, because the
stack is TypeScript/Bun and ours is Python/C++. The value is in interop and
benchmark data.

## Benchmark results (Issue #5848)

**Status: sweep done within a 600 s per-router cap; no kct completion.**
16 source boards are license-checked and pinned, all 16 normalize, and the SRJ
conversion is audited on all 16. Both routers were run on all 16 boards with a
hard 600 s wall-clock cap per (board, router). Within that cap `kct route`
**completed no board** (10 hit the deadline, 6 refused to load), and the
tscircuit autorouter completed 9 of 16 (7 hit the cap). The 600 s cap and a
loaded shared host (load average 15 to 40) mean "did not finish" is a
statement about this budget, not about either router's ceiling. The earlier
single-board Nano run (see below) needed 653 s for kct. The harness is
committed (`benchmarks/external/tscircuit/run_srj18.py`).

Normalization (`normalize.py`): 16/16 succeed after two fixes in this
change. (1) `job_oculink_expansion` contains degenerate (collinear) copper

(2) `rip_up` removed only segments and vias, so **copper arcs survived
normalization** on the 7 boards that have any (dual_gmsl 288, ov9281 88,

`normalize.py` copies it next to the normalized board, so `kct route` and
`kicad-cli` both see the source board's netclass rules.

### What the SRJ abstraction loses

Audited on all 16 `samples/*.json` against the pinned `.kicad_pcb` files.

| Constraint | Source board | In SRJ | Verdict |
|---|---|---|---|
| Track width per netclass | 3 to 12 distinct widths per human-routed board (e.g. Nano: 0.254/0.3/0.4/0.6, Mega: up to 1.27 mm); 15 of 16 boards have *every* segment wider than 0.1 mm | One `minTraceWidth = 0.1` for the board and `width = 0.1` on every connection | **Lost.** Power nets are routed at 0.1 mm. |
| Clearance (board and per-netclass) | e.g. 0.2 mm board rule; 0.5 mm in Nano zone rules | No clearance field. The solver uses its own `obstacleMargin` (default 0.15 mm) | **Lost.** Tighter than the board rule on the Nano. |
| Via size / drill | per board rules | Not in SRJ. The solver defaults to a 0.3 mm via diameter | **Lost.** Below typical fab minimums. |
| Zones (pours) | 0 to 39 zones per board | No zone field. Pours are not obstacles. Zone nets (GND, rails) come through as multi-pin connections, up to 216 points | **Lost.** The autorouter copper-routes nets that a pour would normally carry. |
| Keepouts | 1 to 12 on 4 boards | No keepout field | **Lost.** |
| Existing copper | stripped by `normalize.py` | n/a | Same on both sides. |
| Pads | all | Pads become `rect`/`oval` obstacles with `connectedTo`. Pad shapes beyond that are approximated | Preserved, approximately. |
| Board outline | present | `outline` polyline | Preserved. Edge clearance is not enforced (see below). |
| Layer count | per board | `layerCount` | Preserved. |

Our side had a related loss in the first (Nano-only) run: `fetch_boards.py`
fetched only the `.kicad_pcb`, and KiCad 6 and later keep netclasses in the
sibling `.kicad_pro`. That is fixed (see above), and **the sweep below uses
the `.kicad_pro` for the referee on every board**. `kct route` reads it from
next to its input. The SRJ path still cannot use it: the autorouter only ever
sees the SRJ.

Consequence: any completion score from the SRJ path is for an easier
problem than the board's real one (thinner copper, no pours, no keepouts).
It cannot be compared with a router that honors the board's rules.

### Head-to-head: Arduino Nano (`srj18_arduino_nano`, 2 layers)

> This first run predates the `.kicad_pro` fix: the referee ran with KiCad's
> default rules, not the board's. The sweep table further down re-judges
> the same Nano tscircuit output with the project rules (991 routing-type
> items instead of 1247, `track_width` items gone, `via_diameter` /
> `annular_width` unchanged).

Pinned autorouter: `@tscircuit/capacity-autorouter` 0.0.951, default
`AutoroutingPipelineSolver`, repo HEAD `911963b2` on 2026-09-30. SRJ traces
were written back by `benchmarks/external/tscircuit/srj_to_kicad.py`. Its
coordinate transform was fitted (not assumed) and validated: 179 of 188
obstacles matched, and every matched trace endpoint lands on a pad centre
(median error about 1e-14 mm). The 8 of 228 endpoints that sit more than 0.5
mm from a pad belong to multi-point connections. Vias were written at 0.3 mm
diameter / 0.15 mm drill, because SRJ carries no via size.

`kct route normalized.kicad_pcb --layers 2 --grid 0.1 --timeout 1500`
(C++ backend, `--grid 0.1` because the default grid fails U3's 0.5 mm pitch
escape). Referee: `kicad-cli pcb drc --refill-zones` through
`benchmarks/external/tscircuit/referee.py`. The copper-stripped input
already has 36 routing-type DRC items (32 `copper_edge_clearance` from pads
near the edge, 4 `hole_clearance`), so compare against that baseline.

Notes on reading the table.

- tscircuit completed the board (0 unconnected, 0 shorts) and `kct route`
  did not (68 unconnected, 21 shorts). But the tscircuit result is for the
  relaxed problem above: 0.1 mm tracks, 0.3 mm vias, no pours. The 499
  `clearance`, 199 `track_width`, 140 `via_diameter` and 140 `annular_width`
  items are the constraints SRJ dropped, showing up when KiCad applies the
  board's real rules. By the shared referee, that output is **not
  manufacturable** as written.
- `kct route` kept clearances (4 violations) but left the board incomplete,
  and its output contains 21 shorts and 27 dangling items. The router's own
  log said `clearance_viol=0`, so the post-route self-check missed the
  shorts the referee found. That is a kct defect to fix, not a benchmark
  artifact.
- `kct check` was run (`--drc-only --allow-incomplete`) on every board. It
  exits 2 on all of them, including the human original, because of
  unrelated findings and a missing `current_paths.json`. It therefore did
  not separate the routers and is not used in the table.
- One run, one seed, one board, on a contended host. The wall times are
  indicative of order of magnitude only. Do not read the 465 s vs 653 s gap
  as a speed result.

### Sweep: all 16 boards, 600 s cap per router

Setup: `kct route <normalized> --layers N --grid 0.1 --no-auto-pour
--backend cpp --timeout 600` (N from the SRJ `layerCount`; `--grid 0.1`
because the default grid fails fine-pitch escape; `--no-auto-pour` because
default auto-pour aborts one board, #5864). tscircuit: default
`AutoroutingPipelineSolver` on the dataset's SRJ (`b38e23cb`), 600 s cap,
`node --max-old-space-size=8192`. Referee for every board: `kicad-cli pcb
drc --refill-zones` with the board's `.kicad_pro` next to it
(`referee.py`). 6 concurrent jobs on a shared host, so wall times are not
comparable across rows. KiCad's DRC report appears to cap each violation type
at 199 (several boards show exactly 199 `track_width` items). "DRC" below is
the sum of routing-type items (clearance, shorting, hole, edge, dangling,
width, via, annular, co-located holes). The "Human" and "Normalized" columns

so they give the pre-existing floor.

dangling items are not a verdict on a completed run.

Reading the table.

- **tscircuit completed 9 of 16 within 600 s** with 0 unconnected on 8 of them
  (1 unconnected on `job_oculink_expansion`). It timed out on 7: Mega 2560,
  DDR5 testbed, FTDI toolkit, OCuLink PCIe adapter, OV5640, OV9281 and SDI
  fiber adapter. "Complete" is for the relaxed SRJ problem (0.1 mm tracks,
  0.3 mm vias, no pours or keepouts). Every completed output is **not
  manufacturable as written** under the board's own rules: all 9 carry
  `via_diameter` violations (0.3 mm vias; 90 to 199 each), 8 of 9 carry
  `clearance` items (2 to 498), 5 of 9 carry `track_width` items (the
  0.1 mm tracks), and shorts appear on Leonardo (2), HDMI EDID (2) and
  USB-C (1) with dangling copper on Nano (2), Leonardo (1) and gmsl (3).
- **`kct route` completed 0 of 16 within the cap.** 10 boards reached the
  deadline mid-route (the checkpoint column shows 65 to 342 unconnected
  items left), and 6 were refused at load because of custom-shaped pads
  (#5863: dual_gmsl, gmsl, hdmi, oculink_pcie, ov9281, usb_c). Leonardo is
  among the 10 only because the sweep passes `--no-auto-pour`; with the
  default it aborts before routing (#5864).
- Nothing here says kct is slower than tscircuit in general. Where tscircuit
  finished, it solved a strictly easier problem; where kct was cut off it was
  still routing under the board's real rules. The one honest speed note is
  that on the 5 boards where both routers ran to their caps (Mega 2560, DDR5,
  FTDI, OV5640, SDI fiber), neither finished.
- Not measured: kct with a longer cap on the larger boards, multiple seeds,
  `kct check` (exits 2 on every board including the human originals, so it
  does not separate anything), tscircuit with its rule-aware options (if any
  exist for this version).

### Verdict

Registry: `benchmarked`, pinned at the autorouter commit above. Two things
come out of the 16-board sweep:

1. The SRJ abstraction, as shipped, cannot carry our constraints (netclass
   widths, clearance, via size, zones, keepouts). tscircuit solved 9 of 16
   boards and timed out on 7, but on a relaxed problem, so those numbers are
   not comparable with a router that honors the board's rules. A head-to-head
   on equal terms needs either rules injected into the SRJ problem or the
   tscircuit output re-judged after being widened.
2. The sweep is done, but it is not an equal-terms comparison. kct completed
   0 of 16: 10 boards hit the deadline checkpoint (unverified) and 6 were
   refused at load. Both routers hit their caps on 5 boards. Quote the
   completion rates only with the caveats stated above (unverified
   checkpoints, relaxed SRJ problem, host load, the 199-item cap in the DRC
   report). A longer kct cap is the open follow-up.

Defects found along the way:

- `kct route` ships shorts on the Nano while its self-check reports zero
  clearance violations: filed as #5862 (one completed run, not yet
  reproduced to completion on a loaded host; see the issue).
- `kct route` refuses 6 of 16 real boards on custom-shaped pads: #5863.
- `kct route` aborts under default `--auto-pour` on Leonardo
  (`ZonePartitionError`): #5864.
- Fixed in this change: `normalize.py` failing on `job_oculink_expansion`,
  `normalize.py` leaving copper arcs behind on 7 boards, and
  `fetch_boards.py` not fetching `.kicad_pro`.

### Reproducing

Sweep (all 16 boards, both routers, results as JSON lines):

```bash
export KCT_BENCHMARK_EXTERNAL_CACHE_DIR=/tmp/srj18cache
# fetch and normalize every srj18_* slug first (fetch_boards.py / normalize.py --board ...)
git clone https://github.com/tscircuit/dataset-srj18 /tmp/ds18      # b38e23cb
mkdir /tmp/tsc && (cd /tmp/tsc && npm i @tscircuit/capacity-autorouter@0.0.951)
uv run python benchmarks/external/tscircuit/run_srj18.py --cache /tmp/srj18cache \
  --dataset /tmp/ds18 --tsc-dir /tmp/tsc --work /tmp/srj18work \
  --results /tmp/srj18work/results.jsonl --timeout 600 --jobs 6
```

Single board (Nano):

