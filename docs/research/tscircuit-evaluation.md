# Evaluation: tscircuit as an upstream producer and a peer autorouter

**Date**: 2026-09-30
**Upstream**: https://github.com/tscircuit (organization; many small repos)
**Upstream license**: MIT for every repo examined below, except
`dataset-srj18`, which commits no LICENSE file
**Registry entries**: `tscircuit`, `tscircuit-autorouter`
(`kct ecosystem show <id>`)

## TL;DR

The registry used to file tscircuit under "reference / watch". The reason
was that it exported Gerbers, pick-and-place and BOM files directly and
shared no artifact with us. That is no longer true, and the entry's own
re-evaluation trigger ("first-class `.kicad_pcb` / `.kicad_sch` emission")
has fired:

- **tscircuit is now an upstream producer of KiCad projects.** The CLI's
  build step turns designs into KiCad files through `circuit-json-to-kicad`,
  and `kicad-to-circuit-json` converts in the other direction. It now has the
  same relation to us as atopile and SKiDL: **upstream / complementary**.
- **Its autorouter is a separate peer** that was never registered. It is
  MIT, under active development, uses a different algorithm family from
  ours, and publishes a benchmark derived from real KiCad boards. Registered
  as **peer / watch** until we measure it.

Nothing has been measured yet. The two follow-ups below do the measuring.

## What tscircuit is now

tscircuit describes circuits as TypeScript/React components
(`<board>`, `<resistor footprint="0402" …/>`). `@tscircuit/core` compiles
them to **Circuit JSON**, a flat list of typed elements
(`source_component`, `pcb_component`, `pcb_trace`, `schematic_trace`, …).
Every other tool in the organization is a converter into or out of that
format.

| Repo | Direction | Notes |
|---|---|---|
| `circuit-json-to-kicad` | Circuit JSON → `.kicad_sch` / `.kicad_pcb` / `.kicad_pro` / `.kicad_mod` / library | Staged converters. The PCB converter has stages for nets, footprints, **traces, vias, copper pours**, keepouts and graphics. Its tests run `kicad-cli` against the output. The LICENSE is MIT for code; some interop test artifacts were generated by KiCad and carry KiCad's licenses. |
| `kicad-to-circuit-json` | `.kicad_sch` / `.kicad_pcb` / `.kicad_mod` / `.kicad_sym` → Circuit JSON | Mirrors the pipeline above. Also handles legacy KiCad 5 footprints on a best-effort basis. |
| `kicadts` | read / edit / write | Typed model of KiCad's file format, one class per token, with deterministic formatting. Its tests round-trip the KiCad demo files. |
| `cli` (`tsci`) | build | `cli/build/generate-kicad-project.ts` and `build-kicad-pcm.ts`, so KiCad output is a first-class build target. |
| `jlcsearch` | parts | Constraint-based JLCPCB part search. Overlaps our parts/LCSC tooling in idea only. |

### What it means for us

- A tscircuit design can now reach our pipeline as a native KiCad project,
  so we need no format bridge. Given our mission (agent-driven PCB creation),
  a TypeScript front end that emits KiCad expands who can reach `kct route`
  and `kct check`.
- The quality of that output is **unknown**. Nobody has run a generated
  project through `kct check`, LVS and `kicad-cli pcb drc --refill-zones`,
  our two-engine bar for "manufacturable". Until someone does, treat
  tscircuit as a candidate front end, not a supported one.
- `kicadts` is the closest analogue to our file-handling layer in another
  language. Its round-trip fixtures are a cheap source of edge cases, and
  because it is MIT, ideas and test cases may move with attribution.

## The autorouter (`tscircuit-autorouter`)

Published as `@tscircuit/capacity-autorouter`. The README describes it as
"hundreds of algorithms organized in a Pipeline", using successive
approximation and hypergraphs rather than routing one net at a time
([blog post](https://blog.autorouting.com/p/hypergraph-autorouting)). That
is a different family from our A\* core and from KiCadRoutingTools, which is
itself a reason to measure it.

- **Input**: `SimpleRouteJson`. This is not a KiCad file. It is an abstract
  problem made of layer count, minimum trace width, rectangular obstacles,
  connections and bounds. `@tscircuit/core`'s
  `getSimpleRouteJsonFromCircuitJson` produces it, so a KiCad board reaches
  the router through `kicad-to-circuit-json` → Circuit JSON → SRJ.
  **Any comparison must check that this chain keeps clearances, netclasses
  and zones.** If the abstraction drops a constraint, a benchmark score is
  meaningless.
- **Post-route simplification** is a separate pipeline that takes routed
  traces and only cleans them up. That is comparable in scope to our own
  post-route optimization passes.
- **Bug-report workflow**: a failing route in the tscircuit web editor
  becomes a downloadable fixture and then a snapshot test. This is worth
  comparing with how we turn router failures into regression tests.

### Benchmark data

- `dataset-srj18`: 16 SRJ problems generated from **5 Arduino boards**
  (from `sabogalc/KiCad-Arduino-Boards`, WTFPL) and **11 Antmicro boards**
  (upstream repositories listed in the dataset's `source-files.json`).
  The dataset repo commits no LICENSE, so we **use the source `.kicad_pcb`
  files, not the dataset**. That is the same policy as
  `benchmarks/external/`, which fetches pinned boards at run time and never
  commits them. Check each Antmicro repo's license before pinning it.
- `autorouting-dataset-01`: 200 tscircuit-native problems (MIT). These are
  less useful to us because they are not KiCad boards.

## License position

Every code repo examined is MIT, so `license_compat = "mit-clean"`: code may
move with attribution. In practice we don't expect to move code, because the
stack is TypeScript/Bun and ours is Python/C++. The value is in interop and
benchmark data.
