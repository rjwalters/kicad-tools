- **`mask_to_copper` errors can drop to info** (Issue #8858). Clean same-net pad
  entries now carry disposition `within_own_pad`, at severity info, and the
  assessment can pass with them. Consumers that read
  `mask_copper_assessments[].measurements[].disposition` must accept the new
  value. Info findings never fail `kct check`, including under `--strict`, which
  gates on errors and warnings only (verified). Error counts fall on boards
  routed with 0 mm pad mask expansion. No finding becomes more severe.

- **`mask_to_copper` findings change identity** (Issue #8858). Each finding
  now names `nets` (owner pad + exposed conductor), and `nets` is part of a
  finding's key (`rule_id|items|nets|layer`), so every `mask_to_copper`
  finding's `key` and `evidence_hash` change --
  `mask_to_copper|uuidA,uuidB||F.Mask` becomes
  `mask_to_copper|uuidA,uuidB|GND|F.Mask`. Keyed waivers recorded against
  `mask_to_copper` findings go stale and stop suppressing: the finding
  returns active and can newly fail `kct check`. Re-review and re-record
  with `kct check --waive`.

- **Vendored `check_routed_drc.py` consumers: `mask_to_copper` is no longer skipped** (Issue #8858). If you vendor this gate (Epic #4054), a board whose `--mfr` profile runs `mask_to_copper` and carries same-net copper within the error band beside its own pads' openings will now fail the strict gate. Either repair the copper or add an `identity_allowances:` entry per board in your tolerance YAML (`<pcb path>: <rule>: <net signature>: <tracking issue>`); `count_errors` also returns a third `IdentityOutcome` element now, so unpacking call sites need updating.
