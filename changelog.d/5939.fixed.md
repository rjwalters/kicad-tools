- **`kct detect-mistakes` no longer treats `USB_D+`, `PG_3V3` or `unconnected-(...)` nets as power rails** (Issue #5939).
  The power/ground net classifier matched substrings, so any `+` or voltage
  fragment in a signal name made it a "rail". On board 03 that caused false
  "Missing decoupling capacitor" errors and "Power trace too narrow" warnings
  on the USB data nets. Classification now uses pad pin types (`power_in` /
  `power_out`) when the board has them. Otherwise it falls back to a shared
  whole-token name heuristic (`router.net_class.is_power_rail_name`) that
  strips the hierarchical sheet path first. `VBUS` is now recognised as a
  rail, so its checks may report new findings. The optimizer's FOM
  decoupling term uses the same classifier.
  Voltage-led and P-/V-prefixed rails (`3V3_MCU`, `P3V3`, `V5V0`), `VAA`,
  `VUSB` and qualified `VOUT_*`/`VIN_*` rails still classify as power; `*_SENSE`,
  `*_DET`, `*_EN`, `*_PG` style signals do not. Net `KELVIN_P`/`KELVIN_N` are
  no longer rails (the old `VIN` substring matched inside "KELVIN"). Heads-up:
  `kct optim fom-debug` decoupling-proximity values change (board 04 5.99 ->
  70.24, board 05 31.51 -> 63.91) because the old hint list missed `+3.3V`,
  `VIN`, `VM`; `optim/weights/default.yaml` was calibrated on the old
  classifier. Placement output is unaffected. On board 05, `bypass_capacitor`
  findings rise (95 -> 135) since `VM`/`VIN` are now rails; many pair a cap with
  another cap or diode (Issue #5970).
