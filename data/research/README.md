# Research data artifacts

Committed outputs of the FOM research studies. Everything here is **generated by
a script and must not be hand-edited** — the next regeneration will overwrite it,
and a hand-tweaked number silently detaches from the pipeline that produced it.

The workstreams are split across three trees. This directory is only the middle
one:

| Tree | Role |
|---|---|
| `scripts/research/` | The generators — every file in here is written by one of them. See [`scripts/README.md`](../../scripts/README.md) § `research/`. |
| **`data/research/`** (this directory) | The committed artifacts: datasets, caches, fitted models, plots, weight files. |
| `docs/research/` | The write-ups: method, results, caveats, and the decision each study drove. |

Two independent datasets live here. They share nothing but a parent directory.

| Dataset | Issue | Question | Write-up |
|---|---|---|---|
| [`fom_phase0/`](fom_phase0/) | #3187 | Does any learnable signal exist between cheap placement features and binary manufacturability? | [`docs/research/learned_fom_phase0.md`](../../docs/research/learned_fom_phase0.md) |
| [`fom_weights/`](fom_weights/) | #3188 | What soft-term weights make the FOM rank a committed placement above its perturbations? | [`docs/research/fom_calibration.md`](../../docs/research/fom_calibration.md) |

Interactive companions for both live in [`notebooks/`](../../notebooks/).

## `fom_phase0/` — learned routability residual, Phase 0 feasibility study

A perturb-route-check corpus plus a fitted classifier, used to decide whether a
learned manufacturability predictor was worth escalating to Phase 1.

### File-to-script map

Every file in `fom_phase0/` and the script that writes it:

| File | Written by |
|---|---|
| `labels.jsonl` | `scripts/research/generate_perturbations.py` (`--output` default). Appended row-by-row as each sample completes, so an interrupted run resumes by re-running with the same `--output` and `--seed`. Driven across the board corpus by `scripts/research/run_phase0_corpus.sh`. |
| `labels.parquet` | `scripts/research/train_phase0_classifier.py` — a best-effort parquet snapshot of the JSONL for downstream tooling (needs `pyarrow`; the script logs a warning and continues if it fails). It is *not* written by the perturbation generator, whose `--output` help text is explicit that it emits JSONL only. |
| `negatives.jsonl` | `scripts/research/generate_negative_controls.py` (`--output` default). Kept in a separate file so the training pipeline never sees it. |
| `metrics.json` | `scripts/research/train_phase0_classifier.py` |
| `per_seed_performance.csv` | `scripts/research/train_phase0_classifier.py` |
| `feature_importances.csv` | `scripts/research/train_phase0_classifier.py` |
| `calibration_plot.png`, `feature_importance_plot.png`, `score_distribution.png` | `scripts/research/train_phase0_classifier.py` (note: `score_distribution.png` is emitted by the script but is missing from its module docstring's output list) |
| `classifier.joblib` | `scripts/research/train_phase0_classifier.py`, **only when** global OOF AUC exceeds `--save-threshold-auc` (default `0.70`) |
| `negative_control_report.json` | `scripts/research/check_negatives.py` (`--out` default) |

The generators also use scratch `--work-dir` trees for the intermediate
perturbed/routed PCBs — `data/research/fom_phase0/work` for
`generate_perturbations.py` (both corpus runner scripts pass
`--cleanup-perturbed`) and `data/research/fom_phase0/work_negatives` for
`generate_negative_controls.py`. Neither scratch tree is committed here; delete
them after a run.

### What the labels mean

One row = one perturbed placement. Each non-locked footprint gets an independent
Gaussian `(x, y)` jitter (`--sigma`, plus an optional +/-90 degree rotation via
`--rotate-prob`); the perturbed board is routed and checked; the Phase-0 feature
vector is extracted from the **unrouted** perturbed PCB so a predictor can score
a placement *before* routing. `label = 1` iff routing finished **and**
`kct check` reported zero DRC errors.

`negatives.jsonl` holds three flavours of placement that fail DRC *by
construction* — `edge_violation`, `overlap_pile`, and `extreme_jitter` — as a
confounder check: a model that scores those low is detecting badness, not
detecting "a script touched this".

### `classifier.joblib` is a pickle — treat it accordingly

It is a `joblib.dump` of a dict (`estimator`, `feature_names`, `metrics`) whose
estimator is a scikit-learn `HistGradientBoostingClassifier`. Loadability is
therefore tied to the pinned versions in the `research` extra
(`scikit-learn>=1.7.2`, `joblib>=1.5.3` as of `5cc7690a`); a sufficiently
different scikit-learn will refuse it or warn. It is only present at all because
the study cleared the AUC bar — a re-run that drops below `--save-threshold-auc`
leaves the previous file in place, so check `metrics.json` alongside it rather
than assuming the two agree.

### Regenerating `fom_phase0/`

```bash
# 1. Generate the labelled corpus  (~3 hours of routing)
bash scripts/research/run_phase0_corpus.sh

# 2. Generate negative-control samples  (~30 seconds)
python scripts/research/generate_negative_controls.py --boards-auto --samples-per-flavour 3

# 3. Train + evaluate + dump metrics, plots, and the classifier
python scripts/research/train_phase0_classifier.py

# 4. (optional) Score the negatives against the fresh classifier
python scripts/research/check_negatives.py
```

`scripts/research/run_phase0_fast_corpus.sh` is the shorter-timeout variant used
to add seed diversity within a bounded wall-clock budget; it appends to the same
`labels.jsonl`.

**Determinism.** Every script takes `--seed N` and writes the seed into each
emitted record, so re-running with the same seed reproduces the corpus — *modulo
C++ router non-determinism*, which `docs/research/learned_fom_phase0.md`
("Reproducibility") describes as small but non-zero on this codebase. Expect
near-identical, not byte-identical, labels.

## `fom_weights/` — FOM soft-term weight calibration

Per-board and global weight vectors for the hybrid FOM's soft terms, found by
per-board grid/random search plus an NSGA-II Pareto sweep.

### File-to-script map

All ten files are written by `scripts/research/calibrate_fom.py`
(`--output-dir`, default `data/research/fom_weights`):

| File | What it is |
|---|---|
| `default.yaml` | The global default weight vector — the conservative middle of the Pareto frontier. |
| `voltage_divider.yaml`, `charlieplex_3x3.yaml`, `usb_joystick.yaml`, `stm32_devboard.yaml`, `bldc_controller.yaml`, `diffpair_test.yaml`, `matchgroup_test.yaml` | Per-board best weight vectors (one per in-repo board 01–07). |
| `calibration_report.json` | Per-board weights and metrics, the global weights, the Pareto summary, the train/holdout metrics, and the uniform-weight baselines they are compared against. |
| `term_cache.npz` | Cached per-term raw values, keyed `<board>__committed` / `<board>__perturbed`, so the expensive perturbation-scoring phase runs once. (The script's *docstring* still calls this `term_cache.parquet`; the code writes `.npz` via `np.savez`. The `.npz` name is correct.) |

### These YAMLs are test-gated, not archival

`tests/test_calibrate_fom.py::test_shipped_calibration_yamls_load` globs
`data/research/fom_weights/*.yaml` and asserts that

1. all seven per-board stems above are present, and
2. every YAML in the directory loads as a valid `FOMWeights` with a
   non-negative value for every soft term.

So this directory is load-bearing: deleting a per-board YAML, or dropping any
other `.yaml` file in here, fails the test suite. Add non-YAML files freely;
add `.yaml` files only if they are genuine `FOMWeights` documents.

### Headline numbers

Live source of truth is `fom_weights/calibration_report.json`. As of `5cc7690a`
(2026-08-04): Pareto frontier size 80, selected index 37, selected geometric-mean
rank consistency 0.822 across the five training boards
(`voltage_divider`, `charlieplex_3x3`, `usb_joystick`, `stm32_devboard`,
`bldc_controller`), with `diffpair_test` and `matchgroup_test` held out for the
cross-board validation in `docs/research/fom_calibration.md`.

### Regenerating `fom_weights/`

```bash
uv sync --extra research      # one-time: install pymoo
uv run python scripts/research/calibrate_fom.py
```

A typical run over the 7 in-repo boards takes ~5–15 minutes on a modern laptop.
Non-default knobs (`--perturbations`, `--candidates`, `--pareto-gens`,
`--pareto-pop`, `--output-dir`, `--report-path`) are documented in the script's
`--help`. Note that `--report-path` defaults to `docs/research/fom_calibration.md`,
so a re-run rewrites that tracked file as well as everything in this directory.

**Determinism.** The script is deterministic given `--seed` (default `42`) —
perturbations and weight-search candidates draw from the same seeded RNG
sequence across runs. Pass `--reuse-cache` to keep an existing `term_cache.npz`
instead of re-scoring the perturbations.
