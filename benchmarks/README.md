# Benchmarks

Manual, on-demand placement/routing experiments. **Nothing in this tree is run
by pytest or by CI** — `pyproject.toml` sets `testpaths = ["tests"]`, and no
workflow under `.github/workflows/` invokes anything here. These are scripts a
human runs deliberately when a design question needs numbers, and the committed
results are the record of the run that answered it.

There is currently exactly one suite:

| Suite | Question it answers | Issue |
|---|---|---|
| [`hierarchical/`](hierarchical/) | Does bottom-up hierarchical placement get most of the way there without a cascaded GA? | #2721 |

## `hierarchical/` — bottom-up baseline vs. spacing-proxy GA

### Contents

| File | Kind | What it is |
|---|---|---|
| `hierarchical/run_baseline_comparison.py` | driver | Pure-Python, public-API-only comparison script. Stays on public APIs "so the comparison numbers are reproducible across machines" (module docstring). |
| `hierarchical/results.md` | **generated** | Markdown table of the last run, plus a "Reading the table" key. |
| `hierarchical/results.json` | **generated** | JSON snapshot of the same rows (`BoardMetrics` dataclass, one object per row). |
| `hierarchical/verdict.md` | hand-written | The interpretation: what the numbers mean, why bottom-up wins on one board, and the recommendation. Not regenerated by the script. |

`results.md` and `results.json` are machine output; `verdict.md` is the human
argument built on top of them. Read `verdict.md` first — the table alone does
not tell you which way the decision went.

### Running it

```bash
uv run python benchmarks/hierarchical/run_baseline_comparison.py
```

It reads three **committed, unrouted** PCBs directly — nothing is generated
first:

- `boards/01-voltage-divider/output/voltage_divider.kicad_pcb`
- `boards/02-charlieplex-led/output/charlieplex_3x3.kicad_pcb`
- `boards/03-usb-joystick/output/usb_joystick.kicad_pcb`

Each board is measured under four placements:

1. `input (as-shipped)` — the placement already in the PCB, as a control.
2. `bottom-up` — `place_hierarchical_from_pcb()` with a default
   `HierarchicalPlacementConfig()`.
3. `ga (gen=20, pop=20)` — the evolutionary placer at fast settings.
4. `ga (gen=50, pop=50)` — the evolutionary placer at tuned settings.

### Running it rewrites two tracked files

`main()` writes its output back into this tree:

```python
out_dir = REPO_ROOT / "benchmarks/hierarchical"
md_path = out_dir / "results.md"
json_path = out_dir / "results.json"
```

Both `results.md` and `results.json` are **tracked in git**. A casual run
therefore leaves the working tree dirty with numbers from your machine. Either
restore them afterwards —

```bash
git checkout -- benchmarks/hierarchical/results.md benchmarks/hierarchical/results.json
```

— or commit them deliberately, as a fresh measurement, and update `verdict.md`
to match. Do not let a stray re-run ride along inside an unrelated PR.

### What the metrics mean

| Column | Meaning |
|---|---|
| Wirelength (mm) | **HPWL** — half-perimeter sum of the bounding boxes of component centers, over all multi-pin nets. Lower is better. |
| Overlap pairs | Component pairs whose bounding-box rectangles intersect. Zero is required for a routable placement. |
| Overlap area (mm^2) | Total intersected area. Zero is required. |
| Wall-clock (s) | Single-threaded Python wall time on the dev machine. **Not normalized** — compare ratios between rows of the same run, not absolute numbers across machines. |
| Generations | GA generations actually run (can be fewer than requested if convergence triggered). |

**HPWL is a placement proxy, not routed wirelength.** Routing is deliberately
not run (`verdict.md` § "Out of scope"): the GA inflates board 03's HPWL
several-fold while still producing routable placements, so HPWL alone cannot be
the acceptance criterion.

### Reproducibility conditions actually used

- GA randomness is pinned with a module-level `random.seed(42)` before each GA
  run (`EvolutionaryConfig` exposes no `random_seed` field; the global random
  state is what the GA samples). The bottom-up algorithm is deterministic.
- `EvolutionaryConfig(parallel=False)` — serial, so the comparison wall-clock is
  single-threaded on both sides.
- Both algorithms respect `Component.fixed=True`; connectors (`J*`) and mounting
  holes (`H*`, `MH*`) are fixed in every run.

### Verdict in one paragraph

Bottom-up beat the GA on **one of three** boards (`02-charlieplex-led`, whose
regular 3x3 matrix topology matches the shelf-packer's assumptions) and was
substantially worse on the other two — roughly 123x worse by HPWL on board 01
and 7.7x worse on board 03. But it runs in **under 2 ms** against the GA's
0.2–0.8 s, a 100–400x speedup. The recommendation is therefore to keep the
cascaded-GA architecture and use bottom-up as a **GA seed** (and as a
sub-millisecond "preview" placement), not as a replacement. Full argument, with
the per-board explanation of why board 02 is the outlier, is in
[`hierarchical/verdict.md`](hierarchical/verdict.md).
