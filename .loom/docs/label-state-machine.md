# Holds, and the `loom:operator` state — "a human is needed"

Loom's coordination substrate is labels (see `CLAUDE.md` § "Label-Based
Workflow") — every pipeline transition (`loom:triage` → `loom:curated` →
`loom:issue` → `loom:building`, `loom:review-requested` → `loom:pr`, etc.) is
a label change on an issue or PR. Before `loom:operator` existed, one state
was the exception: "the engine has stopped and a human is the only way
forward." Champion's merge-risk hold expressed that state as an HTML comment
marker (`<!-- champion:merge-risk-hold -->`) buried inside a PR comment —
invisible to `gh pr list`, the dashboard, or any label-filtered query. See
[#5502](https://github.com/rjwalters/loom/issues/5502) for the incident that
prompted this (four Judge-approved PRs sat held-but-invisible for up to 126
hours).

Story points gate `loom:curated`. The Curator writes one
`<!-- loom:points=N -->` marker in the issue body or a curation comment, and
`loom-daemon curation-complete` validates it (the newest trusted comment with
a marker wins, else a trusted author's body), then applies `points:N` (removing
any other `points:*` label) and `loom:curated`. A missing or invalid marker
leaves the issue uncurated. The rubric is in `.loom/docs/story-points.md`.

## The three holds (#11795)

Loom has three hold labels, each with one meaning:

| Label | Meaning | Release |
|---|---|---|
| `loom:blocked` | Waiting on something outside the item: another change merging, a capability, a dependency. The park record or a `Blocked by #N` line says what. Also Champion's own merge-risk and critical-file PR holds (#11861, "Champion's PR holds" below) | A role or a human, once the blocker resolves. Nothing lifts it automatically, with one carve-out (#13331): `merge-pr.sh`'s cleared-blocker notice (`notify-cleared-blockers`) swaps `loom:blocked` for `loom:curated` on an issue whose park records are all `by=curator`, name a blocker, and whose every blocker has merged or closed (no unticked dependency, no `loom:operator`/`loom:frozen`/hard-exclusion label); it never adds `loom:issue`. The daemon's release pass stays retired (#11301). `check-stale-blocked` and `merge-pr.sh`'s cleared-blocker notice report cleared blockers; see [`park-record.md`](park-record.md). Champion releases its own PR holds |
| `loom:operator` | A human must act or decide. The body says which: a ```` ```decision ```` block is a ruling ([`operator-decision.md`](operator-decision.md)); otherwise the comment names the step; a `Blocked by #N` line says the human action waits on something named | A human removes it. Nothing else does |
| `loom:frozen` | Not now; don't touch (#11743). No agent or daemon path reads it as work, comments on it or relabels it | A human removes it |

Every hold is a park, on issues and pull requests alike: dispatch step 2.7
refuses it, so watchdog re-dispatch, checkpoint resume and the epic supervisor
cannot override a hold applied after dispatch (#4366, vibesql#6664), and every
role's discovery, `pr-queue` and the work finder skip it.

**`loom:operator` is a no-op for every role (#11861).** No Curator, Champion,
Judge, Doctor or Builder step acts on it, on an issue or a PR; a targeted run
refuses it before its first write
([`targeted-role-invocation.md`](targeted-role-invocation.md)), and an
explicit user instruction does not override it. Only a human removes it. The
automation's own waits use `loom:blocked`, which the automation re-evaluates.

### How the old labels map

#11795 folded five labels into the three. `loom-daemon labels migrate`
moves open items (closed items keep their labels):

| Retired label | Now |
|---|---|
| `loom:operator-only` | `loom:operator` |
| `loom:operator-decision` | `loom:operator` + a `decision` block |
| `loom:operator-mechanical` | `loom:operator` + a capability marker (a human hold since #11861; relabel it `loom:blocked` to offer it to the capability lane) |
| `loom:operator-blocked` | `loom:operator`; the named blocker stays in the body as a `Blocked by #N` line |
| `loom:needs-capability` | `loom:blocked` + a capability marker |

Three queue labels sit next to the holds and are not holds:
`loom:blocked-unnamed` (the Curator's queue of `loom:blocked` issues naming no
blocker, [`unnamed-block-review.md`](unnamed-block-review.md); no longer
applied since #11301, drained where it remains),
`loom:decision-malformed` (the Curator's repair queue for a bad decision
block, below) and `loom:sequenced` (PR merge ordering, #11708).

## Routing to a human (#10001, #11795)

This is the fleet's one statement of the rule; every role points here.

**Park only for a PO-level decision or a human-hands step.** No hold is a
default for "hard", "uncertain", "two attempts failed" or "I'd rather not":
if an agent could do or decide it, do it, or leave it in the normal queue.
Before applying any hold, the comment says what an agent tried or why it
structurally cannot.

| The situation | Apply |
|---|---|
| A ruling only a human may make: a preference call, or an authority act (binds the entity, irreversible disclosure, spending, credentials only the operator holds, accepting risk on the entity's behalf, physical-world action) | `loom-daemon operator-decision apply <N> --input d.json`: writes the `decision` block (2-4 ranked options, each with a why) and adds `loom:operator` in one write |
| A step needing a human's hands: hardware, a credential or access no fleet host holds | `loom:operator`, plus a comment naming the exact step |
| A human action that waits on something named first | `loom:operator`, plus a literal `Blocked by #N` line in the body or comment |
| Waiting on something automation will resolve: an issue, a PR, infrastructure | `loom:blocked` with a park record (`loom-daemon park-record apply`, [`park-record.md`](park-record.md)), or at least a literal `Blocked by #N` / `Depends on #N` / `Requires #N` line in the same comment (the phrasings `detect-dependency-cycle.sh` and `warn-operator-gated.sh` parse; a backtick-quoted reference does not count) |
| Cross-repo or time-gated leftover (a sweep standing down, not a human ask) | File the child in the other repo and `loom-daemon park-record apply <N> --blocked-by OWNER/REPO#N --by <role> --remove-label loom:building`; the park releases when the child closes. For a time-gated wait, park on the tracking issue or PR whose closing is the signal; with none, file a same-repo tracking issue. If the fleet identity cannot see the other repo (404 on filing), use the capability row below, not `loom:operator`. A reason-only `--reason "wait until <date>: ..."` park is the last resort: **no date release exists today**, so it sits until a human or a fingerprint change moves it, and the reason must say so. Never `loom:operator` just to stop re-dispatch |
| Waiting on a capability a fleet host may hold (host or admin access, a credential profile) | `loom:blocked` with a reason-only park record and a `<!-- loom:capability=<name> -->` marker naming it, plus a linked capability-request issue: the capability lane (below) proposes it on a host that holds it |

**`loom:operator` needs a stated reason class.** Only these classes qualify:
physical (bench, hardware, or an install on an operator machine);
credential/access (grant, mint or rotate); money (spend or a standing cost);
irreversible or outward-facing (publish, delete, migrate, someone else's
system); firewall/legal; decision (a ranked 2-4 option question, best first,
each with a why). A human-hands `loom:operator` comment opens with one
`Operator reason: <class> — <one line>` line. A decision routed through
`operator-decision apply` already satisfies `decision`; add no extra line. An
item that fits no class does not belong: the label comes off and the item
returns to the queue.

**One hold per decision.** The operator's ruling (a dashboard vote, or a
human removing the label) lifts `loom:operator`, so never add an unrelated
`loom:operator` hold to an item that already carries a `decision` block: the
ruling would lift both.

**Unsure which applies means the analysis is incomplete, not that a hold is
safe (#5826).** A decision is never a safe default: run the falsifiability
test below and name the axis two well-informed people would still disagree
on, showing it is a preference, not a fact. If you cannot name it, the item is
determined: finish it. A missing objective is a decision whose options are the
candidate objectives (#10000). An issue's own filing is never operator
approval (#7855, below).

**Composes with the work-finder.** `loom:issue` comes off when a hold goes on
(the atomic transition in `CLAUDE.md` § "Label Discipline"); a human who
removes `loom:operator` from an issue re-adds `loom:issue` to release it.

**Notifier contract.** Loom signals a human ask with labels only (#11087):
no mail, no inbox or chat post, so a notifier failure can never reach a
role's tick. The registry property `human_gated`
(`loom-daemon labels list --property human_gated`) is the authoritative set of
labels that mean "a human must act": `loom:operator` and `external`
(maintainer approval). Not in it: `loom:blocked` (self-clearing),
`loom:frozen` (nothing is pending), `loom:decision-malformed` (Curator
repairs it), and the curation and claim labels. An external notifier (the 2am
`github-events` worker) reads that property instead of hard-coding names,
turns a human-gated label being added into a notification, and resolves it
when the label is removed or the item closes or merges. Pinned by
`label_registry::tests::human_gated_is_exactly_the_human_must_act_labels`.

## Closing out a decision: file what it names (#10940)

A decision comment that names a follow-up ("file X", "handed back to Curator")
is a commitment, and nobody else will act on it. Applying the decision files
or sets that follow-up **in the same pass**:

1. **File each concrete, authorized follow-up** in the **owning repo** with
   `./.loom/scripts/create-issue.sh --repo OWNER/REPO` (never a bare
   `gh issue create`), after `./.loom/scripts/check-duplicate.sh`. If a
   duplicate exists, link it instead of filing. The new issue enters at
   `loom:triage` and links back to the decided issue.
2. **Park the decided issue on it** with
   `loom-daemon park-record apply --issue N --blocked-by OWNER/REPO#M --by <role>`
   (a same-repo ref may be `M`), so the park record is in the body. Never a
   bare `loom:blocked`.
3. **"Handed back to Curator" is one state:** relabel the issue `loom:triage`
   (the queue Curator drains), remove the hold, and say in the comment what
   Curator is to do. A hand-back with no state change is not a hand-back.
4. **File nothing for casual suggestions.** Only a follow-up the decision
   comment states as a commitment, or the operator's ruling authorizes,
   qualifies. Narrative suggestions ("might be worth...") are not filed, and no
   new work is invented from them.

If the fleet credential cannot write to the owning repo, say so in the
decision comment and leave the follow-up named there; do not fall back to
filing it in the wrong repo or drop it silently.

> `loom:operator`: the engine will not work this item further; a human is the

> `loom:blocked`, which Champion re-evaluates.

## Priority labels are not holds (#11103)

Priority is three levels with two labels, `loom:very-important` and
`loom:important` (no label is the default); the model and the dispatch rules
are in [`priority-model.md`](priority-model.md). Neither label is a hold, and
neither is an approval: priority changes the order work is taken, never
whether it is eligible or which gates apply. The operator's star, its
levels and the tier labels are retired (#11103); the old-to-new mapping is
the migration table in `priority-model.md`.

- **Who sets them.** The operator, Guide and Champion add and remove both.
  Builder copies the closing issue's level onto the PR it opens
  (`create-pr.sh`). Nothing propagates priority: the daemon never inherits
  it, and `create-issue.sh --parent N` does not copy it, so whoever sets a
  priority labels a blocker too.
- **Higher level first, every stage.** Curator curates priority issues first
  (no workflow label counts as `loom:triage`) and stops at `loom:curated`
  like any issue. Champion evaluates proposals and epics by level, then age.
  Judge, Doctor and Champion drain priority PRs before their oldest-first
  pass. Builder takes priority `loom:issue` work first.
- **One very-important per workspace.** Only the oldest eligible
  `loom:very-important` issue counts; extras rank as `loom:important`
  (enforced at dispatch, `priority-model.md`).
- **Guards unchanged.** `loom:blocked`, `loom:operator`, `loom:frozen`,
  Champion's merge-risk and critical-file holds and Judge's bar all still
  apply. A priority PR on a hold stays held and is
  listed first (marked ⭐⭐ / ⭐) in the pinned hold digest (#6877).
- **Red-main fixes** are a body marker, not a label: an issue that fixes a red
  `main` carries `<!-- loom:main-red-fix -->` (Doctor adds it when filing a
  pre-existing failure confirmed on `origin/main`). Curator takes these next,
  after priority work, and never promotes them: while that repo's `main` is
  verified red the work finder admits them from `loom:triage`/`loom:curated`
  itself (only when a trusted identity filed them, #9548), and alerts the operator if one stays unclaimed (#10118).

## Champion's PR holds (#11861)

A merge-risk hold (the `merge-risk` criterion) and a critical-file hold (the `critical-files` criterion) are
Champion's own, and Champion must keep re-evaluating and releasing them. Before
#11861 they used `loom:operator`, which was not a park on a PR. Under the
all-role rule they moved to `loom:blocked`:

- `loom:pr` is **kept**: the Judge's approval stands.
- `loom:blocked` is added by `loom-daemon park-record apply --pr N --reason
  "champion merge-risk hold" --by champion` (or `"champion critical-file
  hold"`), which also writes a reason-only park record into the PR body. Only
  Champion or a human releases the hold.
- The hold-state marker comment (`<!-- champion:merge-risk-hold -->` /
  `<!-- champion:critical-file-hold -->`, carrying `champion:hold-state
  head=<sha>`) is unchanged and remains the record of the hold.

**The janitor exception.** `loom:pr` never coexists with `loom:blocked`
("PR verdict-label mutual exclusion" below) except in exactly this shape:
`loom:pr` + `loom:blocked` + a standing Champion hold marker
(`loom_daemon::champion_hold::standing_hold`). The Verdict-State Janitor never
strips `loom:pr` from it, `pr-queue --role champion` serves it (the one park
Champion's queue keeps), and `merge-pr.sh` still refuses to merge it: the hold
is a hold. A `loom:pr` + `loom:blocked` PR with no standing marker is another
actor's park; Champion skips it.

**Exit rule.** The hold is cleared when the artifact **materially changes** —
never merely because Champion re-read the same diff and changed its mind. The
merge-risk hold reuses the release precheck (`champion-pr-merge.md`, "Sticky
holds"); the critical-file hold re-derives its verdict each tick:

| Precheck outcome | `loom:blocked` |
|---|---|
| Never held (`PRIOR_HOLD=false`) | Never applied |
| Held, no release signal yet | Stays applied (idempotent, re-asserted each tick the hold binds; a missing label with no human removal on record is repaired) |
| Released by `loom:auto-merge-ok`, an explicit operator comment, a new push, a new Judge review, or a human removing the label | Removed in the same pass as the reversal comment |

### Releasing a Champion hold and merging it yourself (#9016)

`merge-pr.sh` refuses any PR carrying `loom:pr` and `loom:blocked` at once (the
#8112 verdict-contradiction guard, which has no override flag), so if Champion
put the label back on its next tick, the hold's own "a human merges it
directly" advice would become a race the human usually loses (observed on merge
train #8996). Both holds therefore record the removal instead of overriding it,
and the procedure is two commands in either order, with no tick to beat:

```bash
gh pr edit <N> --remove-label "loom:blocked"
./.loom/scripts/merge-pr.sh <N>
```

- **Critical-file hold** (the `critical-files` criterion): the release is scoped to the **diff**,
  not to a commit id (#9416). Champion acknowledges it once, behind a
  `champion:critical-file-release-respected` marker, and does not re-apply the
  label. A push that changes the diff re-arms the hold; a head move across which
  the PR's own change is *provably* unchanged (`loom-daemon forge
  verdict-equivalent`) does not. See `champion-critical-file-hold.md` and
  `critical-file-hold.md`.
- **Merge-risk hold** (the `merge-risk` criterion): your removal (a human `unlabeled` event
  after the hold) **releases** it (#11416). Champion merges it on its next tick
  unless it finds a concern the hold did not name (the `critical-files`, `mergeable`, `recency` and `ci-green` criteria still apply),
  posting the reversal comment. A human removal of the pre-#11861
  `loom:operator` counts too, so a hold released before the migration stays
  released.

A released hold drops out of the Held-PR Census count but is listed on its
`Released holds, not yet merged` line until it merges (#11416), and it becomes
visible to Doctor's Priority-1 `CONFLICTING` queue again.

### The stale-PR route out of `loom:pr` (#5802, #6720, #6852)

Champion's stale-PR policy swaps `loom:pr` → `loom:changes-requested` on a PR
untouched for 24h, so it reaches Doctor for a rebase; it fires from a **held**
state too (#6720), but only when the PR also carries genuine feedback (a
failing check, #6852; a hold-only stale PR stays on `loom:pr`, untouched).

On that held route **`loom:blocked` stays on** (#11861), so the PR is never a
plain approval while the hold stands, and `merge-pr.sh` refuses it throughout
(it refuses any `loom:blocked` PR, `--allow-unapproved` included). Champion
never removes the label while the hold stands, so a removal is always a
human's release.

The Doctor/Judge round trip still runs under the hold. Doctor's queue
(`pr-queue --role doctor`, the lanes, the targeted path) serves
`loom:changes-requested` + `loom:blocked` when a trusted Champion hold marker
stands (`champion_hold::doctor_may_work`), and Doctor returns it to review as
usual. Judge's queue and review gate serve `loom:review-requested` +
`loom:blocked` the same way (`judge_may_review`); both verdicts leave the label
on, the re-approval restores `loom:pr` + `loom:blocked` (the janitor exception)
and the precheck re-judges the hold. The push is release signal (c).

A held PR whose Doctor cycle is capped (`doctor_cycle_capped`, a trusted
`<!-- loom:doctor-cycle-cap -->` comment the sweep writes) leaves automation's
hands: Doctor skips it and Judge and Champion never see it. The Capped-PR
Recovery Pass, which also reads `loom:blocked` + `loom:changes-requested`,
never grants it a cycle or removes `loom:blocked`; it posts one comment
(`<!-- champion:capped-hold-recommendation -->`) asking a human to review it,
close it or remove the hold, and adds `loom:operator` (the inbox, #11905). Only
a human removes that label (`labels migrate --holds` leaves it); removing it
releases nothing. Find such PRs with
`gh pr list --label loom:blocked --label loom:changes-requested`.

### The out-of-band AC hold on an issue (#6883)

Champion's Step 4 gate applies `loom:operator` to an **issue** whose acceptance
criteria include a step CI structurally cannot perform, when nothing attests it
was performed (`champion-pr-merge.md` → "Out-of-Band Acceptance-Criteria Gate").
A human clears it: by performing the step, posting a comment ending
`<!-- loom:ac-verified sha=<head> -->` and closing the issue, or by rewording a
criterion that was never really out-of-band. There is no automated release,
deliberately: the PR that would re-evaluate it is already merged, and "a human
must observe something in the world" cannot be discharged by an engine re-read.

### The author gate on promotion (#10827)

Champion's content criteria say nothing about who wrote the issue. So before any
**automatic** `loom:issue` write (Champion's Step 3b and the
`check-promotion-landed.sh --apply` backstop) it asks
`loom-daemon forge promotion-author --number N`, which judges the issue **author**
with the same predicate as [`comment-trust.md`](comment-trust.md) (repo insider, a
fleet App, this daemon, `forge.trustedCommenters`, the fleet admin roster), with
no second trust table. Only `TRUSTED` promotes. An `UNTRUSTED` author, or an
`UNKNOWN` one (the issue could not be read), leaves the issue at `loom:curated`
with one comment (keyed on its `<!-- loom:promotion-author-gate rev=… trust=… -->`
marker line, so retries do not repeat it). Unreadable evidence never counts as trust.
The marker records the issue's title/body revision and the trust-rules digest; while a
trusted notice matches both, the step tick excludes the issue from `champion_promote`
(pass reason `author_gate_held`, #13142) instead of re-drawing a session that can only
repeat the verdict. A body edit, a trust-list change, or a legacy unstamped notice
makes it drawable once; a trusted `loom:issue` takes it out of the queue.

**ci-daily tracker exception (#13378).** `promotion-author` also returns `TRUSTED` for an
issue authored by exactly `github-actions[bot]` whose title starts with `[ci-daily] ` and
whose body contains ``opened, updated and closed by `.github/workflows/ci-daily.yml` ``
(the sentence the workflow writes into every tracker); all three must hold. The exception
lives in the author gate only: the bot is not added to `forge.trustedCommenters`, so its
comments and markers stay untrusted everywhere (`forge trusted-comments`, verdict and
hold markers, PRs and non-tracker issues).

Adoption is a trusted maintainer applying `loom:issue` by hand, or re-filing the
issue; an automated Champion verdict alone is not adoption. Trusted authors see no
change. This is admission control for external submissions, not protection against
a compromised trusted agent, and it adds no signed decisions or keys.

## Current implementation

- **The `merge-risk` criterion (merge-risk hold)** — `champion-pr-merge.md`: entry in
  "Hold behavior" (`park-record apply --pr`), exit in Step 2 (`gh pr edit
  --remove-label loom:blocked`, gated on `$HOLD_REVERSAL_BLOCK`), repair in
  the sticky precheck (`LABEL_REPAIR`).
- **The `critical-files` criterion (critical-file hold, #6879, #9016)** —
  `champion-critical-file-hold.md`, run after the `critical-files` criterion's check-loop: add on
  FAIL, remove with the `champion:critical-file-hold-cleared` notice once a push
  leaves every pattern, and respect a human's hand-removal at the held diff.
- **Queues** — `pr-queue --role champion` keeps `loom:pr` + `loom:blocked`
  (and no other park); Judge's and Doctor's queues drop every park.
- **The stale-verdict machinery** (`verdict-staleness-guard.sh`,
  `reconcile_pr_verdicts`) reports a moved head as stale but does not clear a
  verdict on a PR carrying any hold (`loom:blocked`, `loom:operator`,
  `loom:frozen`); re-queueing it would silently un-park it.
- **Migration** — `loom-daemon labels migrate --holds` moves the holds applied
  before #11861 (see "Migrating the holds a role applied" below).

### Migrating the holds a role applied (#11861)

`loom-daemon labels migrate --holds [--repo R | --all-workspaces] [--apply]`
takes `loom:operator` off every open item a role, not a human, put it on. Dry
run unless `--apply`; writes are paced under the shared secondary write limit
(#11789) and a rate limit stops the run for an idempotent rerun.

| Item | Moves to |
|---|---|
| A PR carrying an operator-hold name and a **standing** trusted Champion hold marker, at `loom:pr` or out at Doctor (`loom:changes-requested`) | A reason-only park record and `loom:blocked`, then `loom:operator` itself removed. **`loom:pr` is never touched**, so the approval survives; a PR at `loom:changes-requested` stays Doctor work (Doctor serves a trusted-marker Champion hold) |
| A proposal (`loom:curated` / `loom:architect` / `loom:hermit` / `loom:auditor`) carrying `loom:operator` that Champion escalated for a dependency-only finding (`<!-- champion:proposal-escalated -->`, every recurring finding a dependency with a reference) | Blockers still open: one park record per blocker, `loom:blocked`, `loom:operator` removed, a comment. Every blocker closed: `loom:operator` removed (the #5664 un-escalation, one last time). A cross-repo blocker: left on `loom:operator` |
| An issue carrying `loom:operator` that the daemon's no-op hold parked before #12024 (a trusted `<!-- loom:noop-hold-kind=hold (#10156) -->` notice with no `kind=released` notice after it) | The daemon's `no-op hold` park record (`by=daemon`) and `loom:blocked`, then `loom:operator` removed. A daemon adopts the park from the forge and releases it when the issue's fingerprint changes ([No-op hold](#no-op-hold-10156)). Checked before the escalation row, since such an issue is usually `loom:curated` |
| Anything else, and every retired name (`loom:operator-only`, `-decision`, `-mechanical`, `-blocked`) | Untouched here. The retired names may be a human's: the retired-name migration maps them to `loom:operator`, a park |

Only `loom:operator` itself is ever removed, and only where a trusted Champion
marker, escalation record or no-op hold notice says a role or the daemon
applied it. A no-op hold applied before #11795 under `loom:operator-only` +
`loom:operator-decision` is picked up by rerunning `--holds` after the
retired-name migration.

## Finding what is waiting on you (#8083)

`loom:operator` puts "a human is needed" on the label substrate — but a
state nothing points at is only half-visible. Three
destinations answer "what is waiting on me?", cheapest first.

**1. The two label queries.** Both are one call and neither was written down
anywhere before #8083:

```bash
# PRs Champion is holding on a merge-risk or critical-file hold (#11861):
gh pr list --state open --label loom:pr --label loom:blocked --json number --jq 'length'
# Issues and PRs waiting on a human (the body says which kind, see below):
gh issue list --state open --label loom:operator --json number --jq 'length'
gh pr list --state open --label loom:operator --json number --jq 'length'
```

**2. The merge-risk hold digest — [#6877](https://github.com/rjwalters/loom/issues/6877).**
Champion's Held-PR Census (#6720 / #6851 / #7020) overwrites this issue's body
every pass with one row per held PR — PR number, the hold's own reason, the
`mergeable` status, how long a conflict has been rotting, and (#8552) the PR's
**base-staleness**: whether `main` has moved into the files this PR changes
while it waited, and whether the rebase that implies looks mechanical or
structural — plus an aggregate line. It is **pinned** to the repository so it
is reachable from the
issues page without knowing the number; `champion-pr-merge.md` → "Held-PR
Census" → "Per-PR Digest" → Step 2 re-pins it on **every** pass, so an
unpinned digest self-heals rather than silently staying invisible (the pin is
best-effort and never blocks a merge decision).

The digest carries **both** `loom:blocked` and `loom:operator`, and that
pairing is deliberate:

- `loom:blocked` is what keeps it out of the pipeline. It is a park label
  (`loom-daemon`'s `work_finder::PARK_LABELS`, enforced at dispatch), and the
  digest also never carries `loom:issue`, so no work-finder or sweep path can
  ever pick it up. **Do not remove `loom:blocked` from the digest** — it is
  the whole park.
- `loom:operator` is what makes it *findable*: it is the canonical
  "a human is needed" label, so the digest answers the same query as the
  operator's own inbox. The census reads PRs only (`gh pr list --label loom:pr
  --label loom:blocked`), so the digest, an issue, can never enumerate itself.

**3. `loom-daemon serve`'s dashboard.** Surfacing these counts in
`loom-daemon health` and as an operator-held bucket on `GET /api/pipeline` is
tracked separately in
[#8091](https://github.com/rjwalters/loom/issues/8091) — note that `health`
rolls `overall` up over *every* section, so a new section there interacts with
the #4761 exit-code contract.

## The kind comes from the body (#11795)

`loom:operator` used to be refined by sub-kind labels applied beside a base
label (#5671); 137 of 533 open `loom:operator-only` items already carried a
`decision` block, so the label was a second, drifting copy of what the body
said. Now the body is the only copy:

| Body carries | Kind | Who reads it |
|---|---|---|
| A ```` ```decision ```` block (`operator-decision apply`) | A ruling | The operator UI's decision queue; telemetry `hold_kind` keeps an `operator_decision` stage by reading the block |
| A `Blocked by #N` / `Depends on #N` / `Requires #N` line (alone or with a decision block) | The human action waits on something named first | Humans (Curator's premise re-check is retired, #11861) |
| Neither | A human must act; the comment says what | Humans |

No role acts on any of these (#11861): the kind tells the human what to do.
A capability marker on a `loom:operator` item is inert; the capability lane
reads `loom:blocked` only (below).

### Tracker marker (`<!-- loom:tracker -->`, #10886)

A body marker (not a label, not a hold) for a living tracker or governance hub
that is meant to stay open with no finite deliverable. It must be a line by
itself outside any code fence; a quoted or inline mention does not count.
Champion's Priority 2 discovery skips it and `champion-issue-promo.md` treats it
as `ALREADY_ROUTED`, so no rejection is counted and it never reaches the N=2
escalation; Curator leaves it as found. Remove the marker to restore normal
evaluation. It does not suppress a human-filed `loom:operator` decision.
`loom:needs-capability` waits need no marker: the registry `hold` set covers them.

### Capability marker (`<!-- loom:capability=<name> -->`, #6885/#6892)

The marker states, machine-readably, what capability an item needs. On a
`loom:blocked` item whose only blocker is that capability (no park record
naming a blocker, no decision block) it makes the item one the capability lane
may propose on a host that holds it (#11861; the old `loom:needs-capability`).
On a `loom:operator` item it is inert: no role acts on that label.

**Marker syntax.** Mirrors the `<!-- loom:complexity=<tier> -->` convention
(see `defaults/.claude/commands/loom/curator.md` → "Complexity routing
marker") exactly in form: an HTML comment in the issue/PR body, invisible in
rendered Markdown, trivially greppable. One marker per required capability,
each on its own line:

```html
<!-- loom:capability=host-sudo -->
<!-- loom:capability=cloud-profile:prod-aws -->
```

An item may carry **more than one** capability marker. Multiple markers are
**ANDed** — a worker must hold every declared capability, not just one of
them, before the item is dispatchable. A `loom:blocked` item with no marker
declares no capability and is never lane-eligible.

**Closed vocabulary (small, extensible, fail-closed).**

| Value | Meaning |
|---|---|
| `host-sudo` | Needs root/administrator access on the execution host |
| `forge-admin-token` | Needs a GitHub/Gitea token with admin (not just repo-write) scope |
| `cloud-profile:<name>` | Needs a named cloud credential profile, e.g. `cloud-profile:prod-aws` |
| `tailnet-access` | Needs access to the private tailnet/VPN |

The vocabulary is deliberately small — extend it by adding a row here (and
the matching entry in `defaults/scripts/extract-capability-markers.sh`'s
`KNOWN_LITERALS`/`KNOWN_PREFIXES`), not by any item inventing its own value.
**An unrecognized or misspelled value MUST fail closed**: treated identically
to "no capability declared" (the item stays held), never silently
ignored or treated as satisfied. This applies symmetrically — an item
declaring a typo'd value is exactly as undispatchable as one declaring
nothing, and a worker's own declared holds are checked against the same
closed vocabulary.

**Parser convention.** Anchor to the full `<!-- loom:capability=<value> -->`
comment form, never a bare substring — the same anchoring the retired
complexity-marker gate used, and for the same reason (#4840): prose that merely *quotes* the marker syntax as literal
example text (exactly as this section does above) must never be mistaken for
a live marker. The value grammar is `[a-z0-9][a-z0-9:_-]*`. A
capability-bearing item collects **every** matching marker, deduplicated.
The whitespace immediately before the closing `-->` is optional, and both
reference parsers anchor extraction on the closing delimiter itself (#6914).

The reference implementation is `defaults/scripts/extract-capability-markers.sh`
(tests: `defaults/scripts/tests/test-extract-capability-markers.sh`). The
daemon (`loom-daemon/src/capability.rs`) and sweep parse a body identically
to it, so the two surfaces cannot diverge on what counts as a valid marker.

**Alerters never write a marker.** An alert issue or a Champion merge-risk PR
must never become lane-eligible, and the lane requires the marker.

### Dispatch path (#6893) — propose-only, opt-in per host, fail-closed

Two surfaces read the marker and may route a capability-only `loom:blocked`
item somewhere other than the park (#11861; before, the lane read
`loom:operator`, which no role acts on any more):

| Surface | Where |
|---|---|
| Daemon (Tier 2 dispatch) | `loom-daemon/src/capability.rs` + `WorkItem::is_skipped_with_capabilities` / the `SweepRegistry` step-2.7 park guard |
| Sweep (`all` sentinel + Mode C C0) | `defaults/.claude/commands/loom/sweep.md` → "Capability-aware lane" |

Both apply the **same four gates**, in order, and any failure means "skipped
exactly as before":

1. **The host declares capabilities.** `LOOM_WORKER_CAPABILITIES` (a comma- or
   whitespace-separated list of closed-vocabulary values) is set in the
   *environment*. Unset — the default everywhere — makes the whole path inert.
   It is deliberately **not** readable from `.loom/config.json`: a capability is
   a property of the machine and its credentials, and a file committed to git
   must not be able to assert that the host running it has root.
2. **The item is the capability-only shape**: `loom:blocked` (or the retired
   `loom:needs-capability`), **no** park record naming a blocker, **no**
   `decision` block in the body, and **none** of `loom:operator` or
   `loom:frozen`.
3. **The body declares ≥1 marker and every declared value is recognized** (the
   fail-closed rule above).
4. **The host holds every declared capability** (markers are ANDed).

**What the lane may then do is produce a proposal — never a live credentialed
action.** The worker emits the exact commands (or a PR) for an operator to
approve and stops; the item keeps `loom:blocked` and is not closed. A
live-execution mode is a separate, explicit opt-in that was deliberately not
built.

**When a declared capability is not held**, the item still parks — but the
worker leaves a comment naming the missing capability, turning a silent stall
into a capability request.

**When anything encountered turns out to require a judgement call** rather than
mechanical execution, the worker hard-stops and files a ranked decision
(`operator-decision apply`), which makes the stop durable: gate 2 refuses an
item with a decision block on every later pass.

A `loom:blocked` item that also names a blocker in a park record is **not**
lane-eligible: it waits on another change, which no capability satisfies.
Nothing lifts a capability-only park automatically (it has no named blocker
to resolve): it stays parked until a capable host proposes it or
a human releases it, and the linked capability-request issue says which host
setting would unblock it.

### The falsifiability test, before filing a decision (#5826)

"Requires judgement" does not, by itself, identify work only a human can do —
an agent can research, weigh trade-offs, and rule, given grounding. Before
filing a decision, classify the item along a three-way split instead of
asking "how hard is this call":

| Kind | Definition | Correct response |
|---|---|---|
| **Determined** | The answer follows from physics/constraints/prior art once the analysis is finished — nobody has derived it yet | Derive it. This was never a decision — keep working. |
| **Underdetermined** | Multiple defensible answers survive *full* analysis because the objective function is contested | A decision: the options are the candidate objectives, or the sides of the preference/authority call (#10000) |
| **Authority** | Orthogonal to the above — the act requires authority an agent structurally cannot hold, however determined the answer is (see "Routing to a human") | A decision, or a mechanical `loom:operator` ask, whichever fits |

**The test** — what makes "underdetermined" checkable instead of a vibe:
name the axis along which two well-informed people would still disagree, and
show that axis is a preference, not a fact. If the axis cannot be named, the
item is **not** underdetermined — it is an incomplete analysis wearing a
judgement call as a disguise. Keep working; don't park it. The options' whys
in the decision block carry the axis.

**A missing capability is not operator-by-right.** A block that is really
"automation could do this once a tool/agent capability exists" is
`loom:blocked` + capability marker, linked (`Depends on #N`) to a filed or
reused capability-request issue in the repo that owns the capability, with a
comment on that issue naming what it unblocks (#5817, #5818). An existing
`loom:operator` item of that shape is a human's to re-park (#11861: no role
acts on `loom:operator`); the human can run, in one write:

```bash
loom-daemon park-record apply --issue <number> --blocked-by <capability-request> \
  --by human --remove-label loom:operator
```

**Where this is wired** — every role that can apply the label:

| Role | Site | What it applies |
|---|---|---|
| Champion | Unrevised-proposal bound (`champion-issue-promo.md` Step 4), reached only after the Curator revision loop (#10753) | A ranked decision via `loom-daemon operator-decision apply`; never a bare hold. **Exception, no label applied (#7657)**: when every recurring finding is `premise-false` (a cited path/line-range/repo-state claim, re-verified false on current `main`), Champion closes the proposal (`<!-- champion:premise-false-closed:<main-sha> -->`, `gh issue close --reason "not planned"`) instead of escalating — no hold label, since nothing is routed to a human. |
| Champion | Epic-complete-unpromoted escalation (`champion-common.md`) | `loom:operator` with a `Blocked by #N` line when the recurring finding is itself a live, open dependency; a decision otherwise |
| Champion | Dependency-cycle detector (`detect-dependency-cycle.sh`), capped-PR close recommendation (`champion-pr-merge.md`) | A decision ("breaking a cycle is a human decision" / "the approach itself is not viable") |
| Curator, Builder, Judge, Doctor | "Routing to a human" above, which each role prompt points to | Caller's choice; a human-hands `loom:operator` is the typical Doctor case |

`defaults/scripts/tests/test-operator-hold-routing.sh` fails CI if a role
prompt, doc or script applies a retired hold label, or if a role stops
pointing at "Routing to a human".

### An issue's own autonomous filing is not operator approval (#7855, #8309)

Filing an issue — by any role, including one footed "🤖 Generated with Claude
Code" — is not itself an operator ruling, even when the issue's substance is
a proposal to reverse a documented design decision, safety posture, or a
test's asserted intent. That reversal still needs a decision filed with
`operator-decision apply`; the filing agent's own presence on the issue is
never a substitute for that routing.

**Named anti-pattern**: on #7855, a Curator pass reasoned "the operator
filing it is the ruling that reverses it" about an issue — itself filed
autonomously — proposing to drop the deliberate no-auto-restart posture for a
wedged-but-alive daemon (`loom-daemon/src/watchdog/help.txt` and
`loom-daemon/src/watchdog/mod.rs`'s "no automatic kill/restart" rationale,
asserted by `defaults/scripts/tests/test-loom-daemon-watchdog.sh`'s Test 14).
Champion caught the reversal at the promotion gate, one stage after Curator
had already spent a pass enriching and scoping it on that premise. Do not
restate this reasoning — an issue's own filing, autonomous or not, carries no
approval weight over a documented decision.

This is narrow: it flags proposed *reversals* of existing, documented/tested
behaviour, not autonomously-filed issues in general (see CLAUDE.md § "Issues
Are Suggestions").

**Since #8396 this rule has a mechanism, not only a prose statement.**
`./.loom/scripts/premise-check.sh --issue N` (`loom-daemon premise-check`)
runs **before** Curator enrichment — from the sweep orchestrator's Curator
phase, and from `curator.md` § "Before Starting Curation" on every other
path. For a scoped population (`loom:architect`/`loom:hermit`/`loom:auditor`,
an incident-report heading, or an issue whose own text claims a reversal) it
requires a recorded premise check, and it **refuses** the one combination this
section names as the anti-pattern: a record saying `deliberate=yes
reversal=yes` is admissible only with `verdict=operator-decision`, which is
this exact routing. Exit `11` means "file a decision (`loom:operator` + a
`decision` block) naming the disagreement axis". Contract and design
rationale: [`premise-gate.md`](premise-gate.md).

**`loom:decision-malformed` (#10057)**: the operator UI bounces a
`loom:operator` decision whose `decision` block is missing or invalid into
this label. Curator repairs the block (`operator-decision apply` clears the
bounce label) or, if no operator call exists, removes it and re-routes; a
repeat bounce is left alone. It is a work-finder skip label (#11480), so a
bounced Decision issue is never build work. No daemon release path (claim
release, quarantine release, no-op hold lift, reclaim) re-adds `loom:issue`
beside it or beside any other skip or lane-veto label (#11480's shared
`restore_veto`).

**Champion's revise verdict (#10753, #11860)**: a `NEEDS REVISION` verdict
removes `loom:curated`, adds `loom:triage` and carries a
`<!-- champion:revise:body-<HASH> -->` marker, so Curator curates the issue a
second time against the findings and ends it at `loom:curated` again. Every
Champion evaluation is terminal: promote, revise, block (`loom:blocked` + park
record) or escalate (`loom:operator`). After at most two rounds plus one final
round, Champion files a ranked decision with `operator-decision apply` when a
preference or authority question is named (never a bare `loom:operator`
hold); factual findings get one Curator disposition round first.
`loom:needs-revision`, the label this used to set, is retired onto
`loom:triage` (`labels migrate` also strips `loom:curated`). Contract and
bound: [`promotion-throughput.md`](promotion-throughput.md).

## PR verdict-label mutual exclusion: three independent layers (#8112)

`loom:pr` (approved) must never coexist with a label asserting the opposite
or a pending/blocking hold — `loom:changes-requested`, `loom:blocked`,
`loom:operator`, or `loom:review-requested` — with one exception: Champion's
own merge-risk / critical-file hold, `loom:pr` + `loom:blocked` + a standing
hold marker ("Champion's PR holds" above), which layer 2 leaves alone and layer
3 still refuses to merge (the invariant is stated
authoritatively in `.github/labels.yml`, "PR verdict-label mutual
exclusion"). A contradictory pair is not hypothetical: two Judge passes
reviewing the same head roughly a minute apart reached different verdicts on
PR #4560 (2026-07-30, #4570) and again on PR #8076 (#8112) — nothing about
GitHub's label API is compare-and-swap, so two writers can each read a clean
state and then both still write.

Three independent mechanisms exist for this, at three different points in
the pipeline. None of them supersedes the others — each is a backstop for a
path the others do not cover:

1. **Write-time prevention (chosen remediation for #8112's race, candidate
   (3))** — Judge's and Doctor's **Verdict-Time CAS Recheck**
   (`judge.md` / `doctor.md`) already claims the PR with `loom:reviewing`
   before reviewing and re-reads the label set immediately before writing
   any verdict label, aborting if another verdict already landed, the claim
   was lost, or the head moved. This is the standing mechanism for the race
   itself and predates #8112 (#5686, generalizing the PR #4560 incident
   response) — #8112 does not replace it or add a second one; a Judge/Doctor
   path that skips this recheck is the actual bug to fix if the race recurs,
   not a signal that a new claim/CAS mechanism is needed.
2. **Post-hoc auto-resolution** — Champion's **Verdict-State Janitor Part 1**
   (`champion-pr-merge.md`) runs before Champion's own merge-eligibility
   criteria, detects a `loom:pr` + blocking-label pair regardless of how it
   arose (a race that slipped past layer 1, a manual label edit, a bug
   elsewhere), and resolves it fail-safe: `loom:pr` always loses, the other
   label is kept, and a fresh Judge pass is invited.
3. **Direct-invocation hard block (#8112, this issue)** — `merge-pr.sh`'s
   `_check_verdict_label_contradiction` guard. Layers 1 and 2 both live in
   markdown-orchestrated agent steps, not in the shared script — so a human
   or agent invoking `merge-pr.sh` directly (the documented, canonical way
   to merge; `gh pr merge` is never used, see the root `CLAUDE.md`) bypassed
   both of them entirely, which is the literal gap #8112 reports. The guard
   refuses to merge (hard block, naming both labels) whenever `loom:pr`
   and a blocking label are both present, checking a **fixed list** of
   blocking labels rather than "whichever label happens to be read first" —
   so the refusal cannot be silently defeated by label ordering. Unlike
   layer 2, it does not auto-resolve anything; it stops the merge and leaves
   the contradiction for a human or a fresh Judge pass to sort out, since a
   script invoked directly has no authority to silently discard a
   `loom:changes-requested`/`loom:blocked`/`loom:operator` verdict the way
   Champion's own janitor does under its own auto-merge authority.

**`--allow-unapproved` does not bypass layer 3, and there is no separate
override flag for it either** — this was an explicit decision, not an
oversight. `--allow-unapproved` overrides *absence* of a review signal
("nobody has reviewed this head yet"); the verdict-contradiction guard fires
on *presence* of a conflicting one ("a reviewer explicitly rejected this
head, or it is on hold, or re-review is pending"). Those are different acts:
overriding a missing opinion is a call about risk tolerance for skipping
review; overriding a stated rejection discards someone else's judgment
outright. The remedy for a real block here is the same as layer 2's: get a
fresh Judge verdict on the current head, not force a flag past it.

**Where the blocker is `loom:blocked` from a Champion hold, the remedy is the
hold's own release path, not a fresh Judge verdict** (#9016, #11861) — the approval is
not in doubt, a human decision is. Remove the label and merge; both PR holds
record that removal instead of re-asserting it over you. Procedure and scoping:
["Releasing a Champion hold and merging it yourself"](#releasing-a-champion-hold-and-merging-it-yourself-9016)
above. Nothing about the guard changes for any other blocking label.

## CI-gate recovery (#10178)

A Judge CI-failing verdict leaves `loom:changes-requested` + `loom:ci-failure`.
Head-move invalidation never fires when the head does not move, and refuses a
`loom:blocked` PR. A daemon pass (`claim_reconciliation/ci_gate_recovery.rs`,
behind `LOOM_VERDICT_STALENESS_RECONCILE`) therefore returns such a PR to
`loom:review-requested` once `wait-checks` reports the **exact head** green, and
only for a CI-only verdict (`<!-- loom:ci-gate-only -->`). It never touches
`loom:operator*`, `loom:frozen`, a Champion hold, or a `loom:blocked` that is not
a park record with no blocker and `reason="ci-gate"`.

A CI-only gate must not add `loom:blocked`; if one is unavoidable, park with
`loom-daemon park-record apply --issue <PR> --reason ci-gate --by judge` so the
pass can tell it from a real hold.

## Label registry: the source of truth (#10013)

> **Step dispatch (#11894, live since #11909).** `stale_after_minutes` (live since #11898, see below) is the claim liveness of the five claim labels; a `queued` item state marks a PR in GitHub's merge queue, never drawn for a merge step; and a dead step's claim is restored to its own role's ready stage. See [`docs/design/work-finder-step-dispatch.md`](https://github.com/rjwalters/loom/blob/main/docs/design/work-finder-step-dispatch.md) §12.

`defaults/labels.json` is the single source of truth for label semantics: each
label's name, description, color, `kind`, `applied_by`/`removed_by`, and the
boolean properties the daemon's label tables encode (`park`, `skip`,
`hold`, `operator_gate`, `blocked_colabel`, `hard_exclusion`, `champion_path`,
`human_gated` (the notifier contract, see "Two ways to reach a human"),
`merge_hold`, `operator_hold`, `contradicts_approval`). It is embedded in `loom-daemon`; query
it with `loom-daemon labels list --property park` / `labels get <name>`
(non-zero exit on an unknown label or property). `--with-retired` adds each
retired label whose replacement has the property (#11795): the set a script
matches on while `labels migrate` has not yet relabelled open items.

The Loom block of `.github/labels.yml` and `defaults/.github/labels.yml` is
generated from it: edit the registry, then run `loom-daemon labels generate
--write`. The `label_registry` tests fail on registry drift;
`check-labels-drift.sh` only keeps the two copies byte-identical. The
`quickstarts/*/.github/labels.yml` subsets are deliberately NOT generated:
they are standalone starter templates with no marker block, not held to the
registry.
Every daemon table named by a boolean property above is derived from the
registry, and so are the shell scripts' hold sets (`warn-operator-gated.sh`
queries `operator_gate`; `label_literal_guard.rs` pins the rest). Changes go
in the registry.
The `propagate` table (#10012) was removed (#11510) after #11104 removed
the star-liveness pass that read it. `lifecycle` is inert.
`stale_after_minutes` is live for the five claim labels (#11898): curating 45,
evaluating 45, building 15, reviewing 45, treating 60 minutes (curating,
evaluating and reviewing were raised by #11909 past the 30-minute step
timeout, so a running step's claim never reads as stale). It is the
default claim-liveness window (`loom-daemon/src/claim_liveness.rs`); the env
overrides (`LOOM_STALE_<NAME>_MINUTES`) still win, and `loom:building`'s value
is the lease TTL, because Builder liveness is the renewed lease. A dead step's
claim is restored to its role's ready stage: curating → triage, evaluating →
curated, building → issue (held while the issue's PR is open), reviewing →
review-requested, treating → changes-requested. A retired label leaves `labels` for the top-level `retired`
array (#11513): `{name, replaced_by, owned, retired_in}`, the old -> new
mapping the forge-side migration (#11511) applies. It is never rendered into
`labels.yml`, so `sync-labels.sh` cannot re-create it.

## No-op hold (#10156)

A Builder step that ends `noop` (the step ledger's outcome, except a
`ci_pending` wait), a sweep that self-reports a no-op (the `noop-cooldown
record` IPC), or a Curator-only stop the reaper classifies is counted per issue
against a fingerprint of what the conclusion depends on: labels minus lane
churn (`loom:issue`, `loom:curated`, the claim labels), non-bot comments,
linked-PR state and `## Dependencies` state. An unchanged fingerprint extends
the streak; a changed one restarts it. The streak lives outside the step
ledger, so Champion's promotion verdict, which clears every step cooldown on
the item, does not reset it: a promote / Builder-no-op cycle parks at the
threshold (#12024).

**The streak is the fleet's (#12024).** Each host advertises its own count,
with the fingerprint's digest, on the peer-claim channel (a `noop_streak` ad),
and the hold compares this host's count **plus every peer's count on the same
fingerprint** with `autonomous.workFinder.noopCooldown.holdThreshold` (default
3, env `LOOM_WORK_FINDER_NOOP_HOLD_THRESHOLD`, `0` disables). Three no-ops on
three dispatchers park an issue as surely as three on one. Parking or releasing
publishes a streak break that resets every host's count. Without peer
coordination (`safehouse.enabled` false) the streak is the host's own.

**The park is `loom:blocked`, never `loom:operator`.** At the threshold the
daemon writes a daemon-hold park record into the body
(`<!-- loom:park Blocked by: (unstated) by=daemon at=… reason="no-op hold" -->`),
adds `loom:blocked` (removing `loom:issue`), and posts one
`<!-- loom:noop-hold (#10156) -->` notice that records the fingerprint digest
(`<!-- loom:noop-hold-fp=… -->`). This holds whether the remaining work looks
like a dependency or a human decision: the daemon must be able to release its
own hold, and `loom:operator` is only removed by a human (#11861). A `loom:curated`
issue that no-ops is parked the same way, so Champion does not re-promote it
while nothing has changed. A priority label does not exempt an issue and is
never touched; a `loom:frozen` issue gets no write.

**Release is by fingerprint change.** The daemon re-reads each held issue
(every 5 minutes on the host that parked it, every 30 minutes on a host that
adopted it from the forge) and, once anything in the fingerprint changes (a
comment, a label, a linked PR, a dependency closing), removes `loom:blocked`,
restores `loom:issue` (unless another hold or lane veto is on it) and posts a
`kind=released` notice. Any host adopts a no-op park it finds on the forge (the
park record plus the notice) once per process, so the hold outlives the host
that applied it. A human can also remove `loom:blocked` by hand; the next no-op then starts
a fresh streak.

**Holds applied before #12024** sit on `loom:operator` with the notice above.
The daemon no longer lifts them (it never removes `loom:operator`); move them
with `loom-daemon labels migrate --holds` (dry run, then `--apply`), which
swaps `loom:operator` for the park record and `loom:blocked`; a daemon then
adopts and releases them as above. See
[Migrating the holds a role applied](#migrating-the-holds-a-role-applied-11861).

## Partial-increment remainder hold (#9264)

When a PR merges with a non-closing `Part of #N` / `Contributes to #N` reference,
`merge-pr.sh` returns issue N from `loom:building` to `loom:issue`. If what is left
needs a human's hands or a ruling (an operator decision, a hardware step), the
issue body declares it with an HTML comment marker, added **before** the PR merges:

```text
<!-- loom:remainder-hold reason="needs the operator to flash the board and read back the result" -->
```

With the marker, the reset swaps `loom:building` -> `loom:operator` instead, logs the
reason, and posts a "Partial Increment Merged (remainder held)" comment. To release,
a human removes `loom:operator` and the marker, then re-applies `loom:issue`.

A remainder that is only cross-repo or time-gated (for example a deployment-time check
that waits on a fleet release) is agent work, not a human ask: do not use the marker.
Park it instead, per the "Cross-repo or time-gated leftover" row in
[Routing to a human](#routing-to-a-human-10001-11795).

- The marker is honoured from any author: it can only keep an issue out of the
  ready queue. The `reason` is one line and is only quoted, never evaluated.
- A marker inside a fenced code block is documentation, not a declaration. A marker
  with no or an empty `reason` still holds (the log says the reason is unstated).
- Prose headings ("Deferred", "Needs operator decision") never trigger a hold.
- Wire protocol: `loom-daemon merge-pr partial-reset` prints `SWAP<TAB>loom:operator`
  for a held swap and a bare `SWAP` otherwise; an older `merge-pr.sh` reading the
  former still swaps to `loom:issue`, and a newer script reading a bare `SWAP` does the
  same. Logic: `loom-daemon/src/merge_pr/partial_reset.rs`.
