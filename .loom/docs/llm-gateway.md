# LLM gateway routing for spawned harnesses

A host can route the **metered or API-key** model traffic of the native
harnesses Loom spawns (Pi, OpenCode, Kimi) through a self-hosted LLM gateway:
the harness gets the gateway's base URL and a **virtual key** in place of the
provider's own endpoint and key. Budgets, rate limits and per-request telemetry
then live in the gateway, not in per-host harness config. Claude Code and Codex
never receive any of it (see [the red line](#who-never-receives-it-the-red-line)).

The deployment shape this was built for is 2AMLogic/2am decision D39: a
self-hosted [Bifrost](https://github.com/maximhq/bifrost) gateway with one
virtual key per consumer class (`vk-loom-fleet` for Loom workers), rolled out
one canary worker first, then the fleet. Nothing in Loom is Bifrost-specific
beyond the default virtual-key header name. The implementation is
`loom-daemon/src/worker_spawn/llm_gateway.rs` (#9473).

## The contract

Precedence is **env > config > off**, the same shape as the GitHub App knobs
(`LOOM_GITHUB_APP_ID` beats `forge.githubApp.appId`). `spawn-worker` reads
every setting per launch: a config edit applies to the next launch, and an
environment change applies once the daemon's own environment carries it (a
supervisor restart).

| Setting | Environment | `.loom/config.json` `runtimes.llmGateway.*` | Neither set |
|---|---|---|---|
| Gateway base URL | `LOOM_LLM_GATEWAY_URL` (`off` disables) | `url` | feature off |
| Routed profiles | `LOOM_LLM_GATEWAY_PROFILES` (comma or space separated) | `profiles` (array) | nothing routed |
| Virtual key | `LOOM_LLM_GATEWAY_VK` (the value), else `LOOM_LLM_GATEWAY_VK_FILE` (a path) | `virtualKeyFile` | a routed launch refuses (78) |
| Virtual-key header | `LOOM_LLM_GATEWAY_VK_HEADER` (`none` = bearer key only) | `virtualKeyHeader` | `x-bf-vk` |

- **The URL is the master switch.** With no URL nothing is routed, whatever
  else is set. `LOOM_LLM_GATEWAY_URL=off` disables routing even when committed
  config names a URL, which makes it the one-line break-glass.
- **Routing is opt-in per model profile.** Only profiles named in the list are
  routed; an environment list *replaces* the config list. A launch with no
  profile (an explicit `--model provider/model`) is never routed.
- **The URL is handed to the harness as its provider base URL**, so it names
  the gateway's OpenAI-compatible route (Bifrost: `http://<host>:8080/v1`). It
  must be `http(s)`, with no user-info, query or fragment.
- **The virtual key never belongs in configuration**, which is committed:
  `runtimes.llmGateway` is a closed schema and any other key there (a pasted
  `virtualKey`, say) is a configuration error. The file form holds a bare
  value or one `LOOM_LLM_GATEWAY_VK=value` line, must be an absolute path, and
  must be owner-only (`chmod 600`).
- **Prefer the file.** `loom-daemon-start.sh` harvests exported `LOOM_*`
  variables into the launchd plist / systemd unit, so an exported
  `LOOM_LLM_GATEWAY_VK` lands there in cleartext. `LOOM_LLM_GATEWAY_VK_FILE`
  puts only a path in the unit. The value form is for one-off manual runs.

```json
{
  "runtimes": {
    "llmGateway": {
      "url": "http://llm-gateway.example.net:8080/v1",
      "profiles": ["quick-cerebras", "zai-glm"],
      "virtualKeyFile": "/home/loom/.config/loom/llm-gateway.vk"
    }
  }
}
```

## Turning it on for one host

1. Put the consumer's virtual key in an owner-only file outside every
   repository ([credential policy](credential-storage.md)):
   `install -m 600 /dev/null ~/.config/loom/llm-gateway.vk`, then write the key.
2. Give the daemon's supervisor the three variables, for example a systemd
   drop-in with `Environment=LOOM_LLM_GATEWAY_URL=…`,
   `Environment=LOOM_LLM_GATEWAY_PROFILES=quick-cerebras zai-glm` and
   `Environment=LOOM_LLM_GATEWAY_VK_FILE=…`, then `loom-daemon restart --drain`.
   On launchd, add them to the plist's `EnvironmentVariables` and restart with
   `--reload-supervisor`. This is what makes a canary one host: the fleet
   config can carry nothing at all until the canary passes.
3. Check without launching anything (reads no secret):
   `loom-daemon worker profile-check quick-cerebras --runtime pi` prints
   `llm gateway: routed, url=… credential=CEREBRAS_API_KEY vk=file header=x-bf-vk`
   and `status: resolvable`, or `status: unresolvable, spawn would refuse at
   78 (…)` with the reason.
4. After the next routed launch, its log carries
   `# LOOM_LLM_GATEWAY runtime=… profile=…` next to a `# LOOM_LAUNCH` record
   with `"credentialSource":"gateway"`, and the gateway's own telemetry shows
   the request under the virtual key.

**The gateway must route the bare model name.** Loom sends the profile's
`model` unchanged (`gpt-oss-120b`, `glm-5.3`). With Bifrost that means the
virtual key's provider config lists the model explicitly
(`allowed_models: ["gpt-oss-120b"]` on the `cerebras` provider), so the request
cannot be weighted onto another provider that also serves it.

## What each runtime receives

The virtual key always replaces the profile's own provider-key variable (its
`credentialTargets` entry for that harness, or the `credentialEnv` name), so
the harness presents it as `Authorization: Bearer <key>`. The API-key pool is
not consulted, and the provider's own source variable is removed from the
child: the gateway holds the real provider key. So a routed profile needs no
provider key on the host at all, even one its `credentialEnv` array marks
required: launch, `worker profile-check` and the preference walk all accept it
with only the virtual key configured.

| Runtime | Base URL | Key | Virtual-key header |
|---|---|---|---|
| `opencode` | `provider.<id>.options.baseURL` in the per-launch `OPENCODE_CONFIG_CONTENT` | `options.apiKey` = `{env:<target>}` | `options.headers.<header>` = `{env:<target>}` |
| `pi` | `providers.<id>.baseUrl` in a per-launch `models.json` in Loom's private `PI_CODING_AGENT_DIR` | `apiKey` = `${<target>}` | `headers.<header>` = `${<target>}` |
| `kimi` | `KIMI_MODEL_BASE_URL` (the `providerOptions.kimi.baseUrl` translation) | `KIMI_MODEL_API_KEY` | none: Kimi has no custom-header surface |
| `claude`, `codex` | never | never | never |
| `gemini`, `aider`, generic adapters | never | never | never |

For the two profiles the first rollout targets: `quick-cerebras` on Pi gets
`CEREBRAS_API_KEY=<key>` and a `cerebras` provider override; `zai-glm` on
OpenCode gets `ZHIPU_API_KEY=<key>` and a `zai-coding-plan` provider override
(and `ZAI_API_KEY` removed).

Configuration and logs carry only variable references (`{env:…}`, `${…}`),
never the key. The Pi override needs Loom's per-launch agent directory, which
only a role-tagged (guarded) launch provisions; every daemon dispatch is one.

## Who never receives it (the red line)

Claude Code and Codex run on subscription seats: Claude's OAuth token pool and
Codex's ChatGPT login. Pushing a subscription credential through a gateway is
the shape Anthropic's terms forbid (D39's red line), so no Claude or Codex
launch receives the gateway, even with every knob saying "route". It is
enforced in code at three layers:

1. **The decision** (`llm_gateway::plan`) answers "not routed" for `claude`
   and `codex` before reading any setting, maps only `pi`, `opencode` and
   `kimi`, and refuses a routed profile that does not authenticate with
   exactly one API-key variable: a harness-login profile (a Kimi or Claude Pro
   subscription, an OpenCode `auth login`), a multi-variable provider, or a
   credential variable naming an OAuth token. It also refuses an Anthropic
   credential (`sk-ant-…`) presented as the virtual key.
2. **`spawn-worker`** removes every `LOOM_LLM_GATEWAY_*` variable from the
   process it execs: `spawn-claude.sh`, `spawn-codex.sh`, every other legacy
   adapter, and the native harness itself, which holds a routed key only under
   its own provider-key variable.
3. **The daemon's dispatch surfaces** (the sweep spawn, the role runner's
   tick and the epic supervisor's role dispatch) strip the same variables from
   a child admitted for a runtime that cannot use them, or spawned through
   anything other than `spawn-worker.sh`.

The tests that hold this are
`loom-daemon/tests/worker_spawn_llm_gateway.rs`
(`claude_and_codex_never_receive_the_gateway`: the real `spawn-worker` with
the raw key exported and the profile opted in by env and config, checking that
the Claude and Codex adapters see no gateway variable and no
`ANTHROPIC_BASE_URL` / `OPENAI_BASE_URL`), the unit matrix in
`worker_spawn/llm_gateway/tests.rs`, and one call-site test per dispatch
surface.

## Refusals

A profile the host opted in is never launched around the gateway. These fail
closed at exit 78, before the harness starts, naming the profile and never the
key:

- no virtual key configured, a key file that is relative, missing,
  group/world-readable or not exactly one key, or an `sk-ant-` key;
- a URL that is not `http(s)` or carries user-info, a query or a fragment;
- a virtual-key header that is reserved (`authorization`, …) or not a header name;
- a profile that is not exactly one API key, or that also declares
  `credentialProxy`;
- an unguarded Pi launch, or a Pi launch with `LOOM_NATIVE_AUTH_FILE` set (a
  stored Pi login would outrank the virtual key);
- a contained launch (`runtimes.containment.native`), which does not carry the
  gateway yet;
- an invalid `runtimes.llmGateway` block (checked by every native launch).

## Observability

- The `# LOOM_LAUNCH` record's `credentialSource` is `"gateway"`, with no
  `credentialProvider` or `credentialAccount`, so tap accounting reads
  `pi:quick-cerebras@gateway`. See [telemetry-schema](telemetry-schema.md).
- A sibling `# LOOM_LLM_GATEWAY runtime=… profile=… url=… credential=<variable>
  vk=env|file header=…` line records the route, secret-free.
- Spend and tokens are measured by the gateway (Bifrost: per-request spans and
  log records under the virtual key), not by Loom: the launch record still says
  `"billing":"not-measured"`.
- The ordered runtime preference walk does not gate a routed profile on its
  API-key pool, since the launch never consults it.

## Limits

- One base URL serves every routed profile, so every routed provider must be
  reachable through the same OpenAI-compatible route.
- The model name is sent unchanged; provider prefixing is the gateway's job.
- Contained native launches refuse a routed profile rather than forward the
  key into the container.
