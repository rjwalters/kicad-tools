## The four axes you are actually setting

Every recipe below is a combination of these four, and most operator confusion
is two of them being conflated:

| Axis | The question | Keys |
|---|---|---|
| **Tap** | which CLI, drawing on which credential pool | `runtimes.default`, `runtimes.roles`, `runtimes.preference`, `runtimes.rolePreference` |
| **Model** | which model on that tap | `terminals[].roleConfig.model`, `sweep.tierModels`, `sweep.optimization`, `autonomous.roleRunner.roleModels`, `sweep.escalation` |
| **Capacity** | how many accounts, and what happens when they run dry | `loom-daemon tokens` / `accounts` / `api-keys` |
| **Spend bound** | how much work may fall through to a metered endpoint | `runtimes.backstopCeiling`, `api-keys limit --max-concurrent` |

A **tap** is `(runtime, credential source)`, not a runtime id — the same model
family is reachable through a flat-rate subscription and a metered endpoint with
completely different economics. That distinction is the unit `runtimes.preference`
orders and `sweep-outcomes summary --group-by tap` reports on.

**Where to put a per-host value.** The committed `.loom/config.json` is merged
with `.loom-project/project.json` and then the highest-precedence
`.loom-local/local.json` overlay. Anything true of *this machine only* (a
preference list naming a runtime only this host has credentials for, a backstop
ceiling sized to this host) belongs in `.loom-local/local.json`, which **must
stay gitignored** — unignored it is untracked dirt, and `check-main-clean.sh
--quarantine` stashes untracked dirt between sweep waves, silently reverting the
override (#8075). Confirm with `git check-ignore -v .loom-local/local.json`
before writing anything into it.

## Recipe 1 — put the expensive model on Judge

Judge is reached by **two independent dispatch paths**, with two different pins.
Configure whichever ones your fleet actually runs; setting only one is the most
common way this comes out half-applied.

**Path A — the Judge phase inside a `/loom:sweep`.** Pin it at precedence tier 2,
`terminals[].roleConfig.model`:

```json
{
  "terminals": [
    {
      "id": "terminal-2",
      "name": "Judge",
      "role": "claude-code-worker",
      "roleConfig": {
        "workerType": "claude",
        "roleFile": "judge.md",
        "model": "opus"
      }
    }
  ]
}
```

**Path B — the standalone periodic Judge role tick** (`autonomous.roleRunner`).
It does not read `terminals[]` at all; its model tier is
`autonomous.roleRunner.roleModels.judge`:

```json
{
  "autonomous": {
    "roleRunner": {
      "enabled": true,
      "roles": ["curator", "champion", "judge", "doctor", "guide"],
      "model": "sonnet",
      "roleModels": { "judge": "opus" }
    }
  }
}
```

Here Judge gets `opus` while every other role tick stays on `sonnet`. Precedence
is `roleModels.<role>` > `roleRunner.model` > `autonomous.model` > the shipped
`sonnet` default — see
[`runtime-adapters.md` § Per-role model override](runtime-adapters.md#daemon-runtime-binding-and-admission).

### How the pin interacts with the escalation ladder

`sweep.escalation` (default `["sonnet", "opus"]`) bumps a model one rung when
Judge rejects a PR and a Doctor is dispatched. Two properties matter here:

- **It replaces tiers 3 and 4 only.** An explicit dispatch model (tier 1) and a
  `roleConfig.model` pin (tier 2) always win, so a Judge pinned to `opus` is
  never escalated away from — and never escalated *up* either.
- **It fires on the rejection-triggered Doctor, not on Judge.** Escalating
  "the reviewer" is not what the ladder does; if you want an expensive reviewer,
  pin it, do not rely on escalation.

If you pin Judge to `opus` and want Doctor to stay cheap, give Doctor its own
`roleConfig.model` / `roleModels.doctor` — otherwise it inherits the ladder.

### `opus` is a logical tier, not a wire model

The bare `opus` alias resolves through `sweep.modelAliases` (shipped map pins
only the stale tier). Keep writing `opus` in config and repoint the map if you
need a different concrete ID — do not hand-pin an ID in five places. Details:
[`model-selection.md`](model-selection.md).

### Judge independence — and the trap in getting it via `runtimes`

There is a real reason to want Judge on a *different tap*, not just a different
model: a **native sweep runs every phase in one session with no subagents**, so
the reviewer is literally the process that wrote the change.

`runtimes.rolePreference.judge` is the key for that — but read this before
reaching for it:

> **A full sweep dispatch resolves its runtime under the `sweep-lifecycle` role
> key, not `judge`.** A sweep is one runtime throughout (admitted against
> *Builder's* capability requirements, the strongest in the lifecycle), and a
> per-role binding cannot switch runtimes between phases. So
> `rolePreference.judge` / `runtimes.roles.judge` govern the **standalone
> periodic Judge tick** (Path B above) — not the Judge phase inside a sweep.

Which makes the working shape explicit: let the sweep open its PR with
`loom:review-requested`, and let a **standalone Judge tick on a different tap**
review it.

```jsonc
// .loom-local/local.json — per-host, gitignored
{
  "runtimes": {
    "rolePreference": {
      "sweep-lifecycle": ["claude", "codex", "opencode"],
      "judge": ["codex", "claude"]
    }
  }
}
```

**Do not set a role's runtime without its matching model.** `runtimes.roles.<role>`
and the model tier are resolved independently; a Claude-shaped alias forwarded to
a Codex adapter is an HTTP 400 that the classifier treats as recoverable, so the
tick retries forever. Since #5028 a pre-spawn check refuses instead — which is
better, but still means *zero* ticks for that role. Pin both axes, or pin the
model to the `"default"` sentinel (the only shape a ChatGPT-plan Codex seat
accepts):

```json
{
  "runtimes": { "roles": { "judge": "codex" } },
  "autonomous": { "roleRunner": { "model": "sonnet",
                                  "roleModels": { "judge": "gpt-5-codex" } } }
}
```

A role-runtime pin also **moves which credential pool that role draws on** —
see Recipe 4 for the worked example where this silently stopped a fleet's Judge.

## Recipe 2 — minimize wall-clock on code work

The one-line answer:

```json
{ "sweep": { "optimization": "speed" } }
```

`sweep.optimization` is `"cost"` | `"speed"` | `"balanced"` (default
`"balanced"`), with env override `LOOM_SWEEP_OPTIMIZATION` (**env > config >
default**). The shipped presets, quoted from
[`model-selection.md`](model-selection.md#optimization-profile-switch-sweepoptimization-issue-4238-phase-b):

| Profile | `mechanical` | `routine` | `complex` |
|---|---|---|---|
| `balanced` (default) | *(unset)* | *(unset)* | *(unset)* |
| `cost` | `haiku` | `sonnet` | `opus` |
| `speed` | `sonnet` | `opus` | `opus` |

**Why `speed` starts a tier higher rather than picking a faster model.**
Wall-clock in a sweep is dominated by Judge-rejection / Doctor **round-trip
count**, not per-turn latency. One avoided rejection is worth more than every
token of latency you could shave, so `speed` buys fewer retries. `complex` is
already at the ceiling under `balanced`, so `speed` raises `mechanical` and
`routine` and leaves `complex` alone.

### What decides which stratum an issue lands in

The Curator's `<!-- loom:complexity=<tier> -->` marker, on the one axis *how
expensive is it to be wrong?* An issue with no marker counts as `routine`. This
is a Curator output, so an unenriched issue gets the middle tier by default — if
your `mechanical` work is not getting the cheap rung, check the marker before
touching the config.

### Hand-tuning one stratum

An explicit `sweep.tierModels[<runtime>][<tier>]` entry **wins over the preset**,
so you can take a profile and override exactly one cell:

```json
{
  "sweep": {
    "optimization": "speed",
    "tierModels": { "claude": { "mechanical": "haiku" } }
  }
}
```

That is `speed` everywhere except `mechanical`, which stays cheap. The map is
runtime-neutral in its *tier* names, keyed by runtime for its *model IDs*
(`"codex": { "routine": "gpt-5", … }`).

### The bounds you cannot configure around

Tier routing is **Builder-only**, **never resolves to `fable`**, is suppressed
for the forced arm in model-cost experiment mode, and — the one that bites —
**tier-1 and tier-2 pins still win**:

> Pinning `terminals[].roleConfig.model` for **Builder** disables tier routing
> for Builder entirely. Tier routing sits at precedence 2.5, *below* the
> workspace pin. `sweep.optimization` and a Builder `roleConfig.model` pin are
> mutually exclusive in practice — pick one.

Raising `sweep.max_doctor_cycles` above its default of `1` does the opposite of
this recipe: it buys more repair attempts at the cost of more round trips (and
activates deeper escalation rungs automatically).

## Recipe 3 — throttle and capacity backstops

Four layers, cheapest first. Most fleets need only the first two.

### Layer 1 — more accounts in the pool you already use

Claude OAuth rotation is the baseline. Provision *outside* the repo and rank:

```sh
loom-daemon tokens bootstrap --shared      # or: import-from-monitor --shared --force
loom-daemon tokens check --ranking
```

When the pool is present but fully exhausted, Loom **stops rather than burns
spawns**: sweep dispatch holds the host (#7708) and role ticks skip before spawn
(#7607) instead of exiting `78` ten seconds in. Both self-heal on the next tick
when a window rolls over. Full mechanics: [`token-pool.md`](token-pool.md).
Credentials stay outside every repo and worktree —
[`credential-storage.md`](credential-storage.md).

### Layer 2 — ordered fall-through across taps

`runtimes.default` picks *one* runtime and cannot express "prefer the seats I
already pay for, fall through only when they are dry". `runtimes.preference`
can:

```jsonc
{
  "runtimes": {
    "preference": ["claude", "codex", {"runtime": "opencode", "modelProfile": "zai-metered"}],
    "rolePreference": { "judge": ["codex", "claude"] }
  }
}
```

Resolution walks the list and takes the first tap that is **(a)** admitted for
the role and **(b)** has a spawnable credential right now. Four things to know
before writing one (full contract in
[`runtime-adapters.md` § Ordered runtime preference](runtime-adapters.md#ordered-runtime-preference-with-fall-through-issue-8436)):

- **Codex is never admitted for Builder or Doctor** (`worktreeIsolation:
  "partial"`), however high it sits. `["claude","codex","opencode"]` is
  effectively `claude → opencode` for build work; the skip is recorded as
  `not-admitted(worktreeIsolation)`, which is not the same as "no credential".
- **An operator pin disables fall-through outright.** `LOOM_RUNTIME`,
  `LOOM_RUNTIME_<ROLE>`, or an explicit per-dispatch runtime short-circuits to
  static resolution — deliberately, so a pin stays useful for debugging.
- **`modelProfile` currently gates but does not pin** (#8602): availability is
  read against the named profile's pool, but the launch resolves whatever profile
  that runtime would have used anyway. Prefer **bare** runtime entries unless the
  named profile *is* that runtime's default.
- **Fail-closed stays fail-closed.** When every listed tap is skipped the caller
  holds exactly as before; the list only widens what counts as "available".

### Layer 3 — bound the metered tap

Every tap except a metered one is flat rate: overusing it costs nothing extra and
it recovers on a clock. A metered pay-per-token endpoint effectively never
exhausts, so nothing stops it — an all-day Claude outage routes the entire
backlog through it, unnoticed, because falling through is what the resolver is
*supposed* to do. `runtimes.backstopCeiling` is the bound:

```jsonc
{
  "runtimes": {
    "preference": ["claude", "codex", {"runtime": "opencode", "modelProfile": "zai-metered"}],
    "backstopCeiling": {
      "maxConcurrent": 2,          // most concurrent metered dispatches this HOST may hold
      "appliesFrom": 2,            // first tier the ceiling governs (default 1)
      "minComplexity": "complex"   // work below this stratum never reaches a governed tap
    }
  }
}
```

- `maxConcurrent: 0` switches the metered tier off without editing the preference
  list. Env override: `LOOM_BACKSTOP_MAX_CONCURRENT`.
- `appliesFrom` is 0-based and **must be ≥ 1** — tier 0 is the subscription you
  already pay for, and bounding it inverts the purpose. `0` is a config error.
- This is a **spend ceiling, not a cooldown**: a refusal is recorded as a skip
  and the walk continues, and an unreadable lease store yields `ceiling-unknown`
  and a skip rather than guessing "there is room".
- State is **per host** (`~/.loom/leases/backstop/`). A fleet-wide ceiling over a
  key shared *between* hosts is explicitly out of scope — that needs
  provider-side budget controls.

### Layer 4 — per-account concurrency on an API-key pool

For native-harness taps whose credential is an API key (Z.ai/OpenCode, Pi, Kimi),
`loom-daemon api-keys` is the rotation pool, and it can carry a provider-side
concurrency cap per account:

```sh
loom-daemon api-keys add zai alice --key-file /path/to/key
loom-daemon api-keys limit zai alice --max-concurrent 2      # or --unlimited
loom-daemon api-keys health --provider zai
```

Selection **enforces** the cap: an account already holding N live spawns is
skipped in favour of another eligible one and becomes selectable the instant a
spawn exits — no cooldown, no operator action. A pool whose every account is
capped out fails closed at `78` naming the cap.

**Bad marks are automatic as well as operator-invoked.** After a native sweep or
role tick exits, Loom re-reads that run's own retained log and bad-marks the
account when the log says its allowance ran out (429, `insufficient balance`, …).
Two consequences worth internalising:

- It is **post-hoc**, not live interception — the mark lands when the run exits,
  and a run whose output is never retained is never ingested.
- **An auth failure (401) is never bad-marked.** On OpenCode 2.x a 401 is also
  what a correct key looks like when the launch forgets `--standalone`, so
  marking on it would pull a healthy account for a launch-config bug.

Marks self-heal at their reset horizon; `--model-class` scopes a mark to one
allowance so an exhausted flash model leaves the account selectable for the
others. Full contract: [`runtime-model-trials.md`](runtime-model-trials.md).

## Recipe 4 — verify what you configured

### Step 1 — does the config parse and mean what you think?

```sh
loom-daemon validate                 # or: loom-daemon validate /path/to/workspace
loom-daemon validate --strict        # exit 2 on warnings, for CI
```

It **catches** malformed resource config, with the offending key named:

```text
ROLE CONFIGURATION ERRORS:
  - runtimes.roles: unknown role name(s) in runtimes.roles: buidler (known roles:
    architect, auditor, builder, champion, curator, doctor, driver, guide, hermit,
    judge, sweep-lifecycle)
  - runtimes preference: runtimes.preference lists claude more than once; a duplicate
    entry can never be reached and is more likely a typo than an intent
  - runtimes backstop ceiling: runtimes.backstopCeiling.appliesFrom must be >= 1 …
```

It does **not** catch a model/runtime *mismatch* — `runtimes.roles.judge =
"codex"` with `roleModels.judge = "sonnet"` validates clean. That is a
**spawn-time** refusal (#5028/#6201); see step 3.

Native-harness profiles get their own pre-dispatch proof — the harness +
provider + model ID resolve, or the launch is refused before it runs:

```sh
loom-daemon worker profile-check gemini-flash            # reads no secret values, contacts no provider
loom-daemon worker profile-check gemini-flash --runtime pi
```

An unresolvable profile exits `78` naming the bound harness — so "which model
is the default even" is answered *before* dispatch. For an unset credential
variable a pooled provider could supply, the check also names the pool
namespace and its selectable count, still without reading any account's value
(full contract: [`runtime-model-trials.md`](runtime-model-trials.md) §More models).

### Step 2 — which tap actually ran?

Two sibling stderr markers, never merged into one line (the crash-signal reader
takes the whole rest of a `# LOOM_RUNTIME_RESOLVED` line as the runtime name):

```text
# LOOM_RUNTIME_RESOLVED runtime=claude
# LOOM_RUNTIME_PREFERENCE order=claude,codex,opencode tier=0 tap=claude source=role-preference
```

`# LOOM_RUNTIME_RESOLVED` lands in the per-sweep log (`.loom/logs/sweep-issue-<N>.log`).
`# LOOM_RUNTIME_PREFERENCE` lands in the **daemon log** (`~/.loom/daemon.log`) —
writing it into the per-sweep record too is tracked in #8599.

```sh
grep '# LOOM_RUNTIME_RESOLVED'   .loom/logs/sweep-issue-*.log | sort | uniq -c
grep '# LOOM_RUNTIME_PREFERENCE' ~/.loom/daemon.log | tail
```

"How much work is going to the backstop" reduces to counting markers whose
`tier` is not `0`. A launch that consumed a ceiling slot appends `backstop=1/2`
to the same line; a refused one is recorded on the skipped tap as
`ceiling-at-capacity` (working as designed), `ceiling-ineligible` (a policy
verdict) or `ceiling-unknown` (a host fault to repair).

### Step 3 — which model, from which tier, for a role tick?

`.loom/logs/role-<role>.log` carries a dated header per tick naming the resolved
model **and the precedence tier that supplied it**, so a pin is confirmable from
the log alone:

```text
==== loom-daemon role_runner: … role=judge model=sonnet (source=default) effort=… ====
```

The same file is where a pre-spawn refusal lands. **A worked example from this
repo's own install**, which is exactly the Recipe-1 trap in the wild:

```text
==== loom-daemon role_runner: 2026-09-23T06:30:10Z role=judge SKIPPED BEFORE SPAWN (#6201):
codex account pool exhausted: 0/0 spawnable in `loom-daemon accounts` (provider codex; no
enabled codex account is provisioned); the Claude token pool is not consulted for the codex
runtime; next check ~… — run `loom-daemon accounts list` … ====
```

`runtimes.roles.judge = "codex"` was set on a host with no Codex account
provisioned, so every standalone Judge tick was skipped — 157 such lines, and
`loom-daemon validate` was green throughout. **A role-runtime pin moves which
credential pool that role draws on**; the pre-spawn gate follows the admitted
runtime (#8408), and the Claude pool is not consulted for a non-Claude runtime.
Always confirm a role pin against its pool:

```sh
loom-daemon accounts list            # codex seats
loom-daemon tokens check --ranking   # claude OAuth pool
loom-daemon api-keys health          # api-key pools
loom-daemon health                   # consolidated, with an exit-code contract
```

### Step 4 — what did it cost, by tap?

```sh
loom-daemon sweep-outcomes summary --group-by tap
loom-daemon sweep-outcomes summary --group-by tap --since 7d
```

`--group-by tap` cuts by `(runtime, credential source)` — the one dimension whose
economics actually differ, and the cut *"how much went to the metered backstop
vs. the subscriptions"* reduces to. Two caveats the command prints rather than
hides: every counter is optional, so a missing one means **unmeasured, not
zero**, and the weighted-token figures price through a named, known-stale rate
card. The cost field is `tap_cost_estimate` — an estimate for a metered tap and
**not a charge at all** for a flat-rate one.

## Recipe 5 — cheap fast default model (e.g. Gemini Flash)

The inverse of Recipe 1: instead of paying for the expensive subscriptions
fleet-wide and pinning the expensive model on Judge, run the **default** on a
cheap, fast model and promote only the quality-critical roles. Recipe 1 owns
the promotion; this recipe owns everything that stays cheap.

### The harness has to be native

Claude Code (Anthropic-only) and Codex (OpenAI-only) cannot serve a
`gemini-*` model. Pi and OpenCode can, through the model-profile mechanism,
for any provider ID their CLI knows. Put the chosen CLI on `PATH` (or set
`LOOM_PI_BIN` / `LOOM_OPENCODE_BIN` to its executable) and authenticate it per
the profile's credential mapping. Kimi Code CLI is the third native harness but
is not yet guarded for Judge (no verified `loom_*` tool binding), so a quality
tier on it fails closed at exit `78`.

### The flash profile is the one indirection point

Define it once under `runtimes.modelProfiles` and make it the default:

```json
{
  "runtimes": {
    "default": "pi",
    "defaultModelProfile": "gemini-flash",
    "modelProfiles": {
      "gemini-flash": {
        "model": "gemini-2.5-flash",
        "providers": { "pi": "google", "opencode": "google" },
        "credentialEnv": "GEMINI_API_KEY",
        "credentialTargets": { "pi": "GEMINI_API_KEY", "opencode": "GEMINI_API_KEY" }
      }
    }
  }
}
```

**"Latest flash" is a moving target.** Verify the `model` ID against the CLI's
own model list on the day you write it — Recipe 4's `worker profile-check`
refuses an ID the runtime cannot resolve. When the provider rotates the flash
line, edit *this object* and nothing else: no per-role or sweep config names
the raw ID. That is the same single-indirection property `sweep.modelAliases`
gives the escalation ladder ([`model-selection.md`](model-selection.md)).

The profile **names variables only** — the key value rides in the launching
environment or an api-key pool (`loom-daemon api-keys add gemini <account>
--key-file …`), never in config ([`credential-storage.md`](credential-storage.md)).
A Vertex / ambient-cloud-credential deployment uses the multi-variable shape:
`credentialEnv` as an array, a per-variable `credentialTargets.opencode` map,
provider `google-vertex` — the bundled `example-vertex` in
`defaults/model-profiles.json` is the template.

### Keep the default cheap: leave the runner's global model tier unset

Profile selection for the native adapters is `--profile` > `LOOM_MODEL_PROFILE`
> `runtimes.defaultModelProfile` > the shipped `zai-flash`. The rule that makes
this recipe work: **an unconfigured native role runs its selected profile —
never the shipped Claude `sonnet` alias.** So leave
`autonomous.roleRunner.model` unpinned; that is what keeps the un-promoted
majority on flash. (If you do pin it, pin something the native runtime
accepts — a qualified `provider/model` or the profile's model name. A Claude
alias trips the #5028 mismatch preflight: Recipe 1's trap, same shape.)

### Promotion: the native pin rule, and the judge-independence trap

The per-role pins work exactly as in Recipe 1; two things differ on a native
runtime.

- **Explicit pins must be qualified `provider/model`** (or match the resolved
  profile's model exactly). The native adapters do no fuzzy Claude-alias
  translation and no silent provider fallback, so "one rung up on the same tap"
is a qualified ID, e.g. `"roleModels": { "judge": "google/gemini-2.5-pro" }`,
  not a bare tier name.
- **Judge independence.** A native sweep runs every phase in **one session with
  no subagents** — the fast model that wrote the PR would be grading its own
  work. Recipe 1's trap paragraph applies verbatim:
  `rolePreference.judge` / `runtimes.roles.judge` govern the **standalone
  periodic Judge tick**, not the sweep's Judge phase (a sweep resolves under
  `sweep-lifecycle`). The working shape is therefore unchanged: the sweep opens
  its PR at `loom:review-requested` and a **standalone Judge tick on a
  different tap** (e.g. the Claude subscription) reviews it.

### Interactive sweeps: the fast model is the session's tier-4 default

The session's own model is tier 4 of the model-selection chain: start the
orchestrator session on the fast model (a Pi/OpenCode session whose selected
profile is the flash one), and every unpinned role inherits it. Pin the quality
roles per Recipe 1 Path A — `terminals[].roleConfig.model` at tier 2, or the
role's `suggestedModel` (the shipped Judge default is already `opus`) — and a
pin outranks the `sweep.escalation` ladder for that role.

## Interaction rules that bite

| If you… | Then… | Owner |
|---|---|---|
| pin `terminals[].roleConfig.model` for Builder | `sweep.optimization` / `sweep.tierModels` stop applying to Builder (tier 2 beats tier 2.5) | [`model-selection.md`](model-selection.md) |
| set `runtimes.roles.<role>` without `roleModels.<role>` | the tick is refused before spawn, forever, and `validate` stays green | [`runtime-adapters.md`](runtime-adapters.md) |
