# `merge-pr.sh` exit codes 3-7 — the "not a failure" outcomes

`merge-pr.sh` reserves exit codes 3, 5 and 7 (4 is retired, #12063) for outcomes that look like failures to
a naive `|| handle_failure` caller but are not: the merge did not happen,
nothing is wrong, and the correct response is to re-queue the PR for a later
pass.

One more outcome joined them in #9096 and is covered here too: **no exit code at
all**, when the caller is killed before the script can return one. It is not a
"not a failure" outcome — it is a *not-an-outcome*, and unlike the ones below
it does get a PR comment.

Champion's operative handling lives in
`.claude/commands/loom/champion-pr-merge.md` →
"Exception: exit codes 3-7". Exit 7 has two sources, both silent re-queues:
`merge-pr.sh`'s sequencing hold (#11330), and Champion's Step 3, which sets it
itself when `loom-daemon forge merge-queue step` withholds the direct merge so
`merge-pr.sh` never runs (see the two "Exit 7" sections below). This file holds
the rationale, the design decisions behind it, and the forensics notes — the
parts a Champion session does not need loaded to act correctly.

## Exit-code table

Every caller that branches on `merge-pr.sh`'s exit (Champion Step 3, the sweep
merge step, a hand-rolled driver) uses this table. An unknown non-zero code is a
failure — the safe degradation for a caller older than a new code.

| exit | retryable? | cause | caller action |
|---|---|---|---|
| `0` | — | Merged. | Done. |
| `1` | no | Everything else: a real refusal or failure, including a merge the forge refused as unmergeable (conflict, not allowed) and a red required context (#10688; `--allow-red-required <context>` overrides one named context). | Failure handling (Champion's "Merge Failed" comment). |
| `3` | yes | The PR's head moved between the fresh head-SHA read and the merge call (#5579) — someone else moved it. | Re-queue; the verdict does not carry to the new head (#5686). |
| `4` | yes | Retired (#12063): never emitted. Was the #8508 re-date push. | Re-queue if seen from an older script. |
| `5` | yes | Held: a required context is missing or pending on this head (#10688, caught before the call so a bypass-capable token cannot walk past it), or the forge refused the merge call because a required status check is pending or red (#12063). `merge-pr.sh` waits for nothing. Nobody moved the head. | Re-queue. |
| `7` | yes | `merge-pr.sh`: the PR carries `loom:pr` + `loom:sequenced` and no other blocker; stdout carries `LOOM-SEQUENCED-HOLD pr=<N> after=<M>` (#11330). Or *(Champion Step 3 only)* `forge merge-queue step` gave no `LOOM-MERGE-QUEUE-DIRECT` verdict (#10256, #10628). | Re-queue, like 6. The sequencing hold clears when `<M>` lands (`merge-pr sequence-eval`); a queue stall is surfaced by Step 3. |
| `8` | no, re-evaluate | Only with `--expected-head <sha>` (#11859): the PR head is not the SHA the caller evaluated, on the first uncached read or the merge precondition read. stdout carries `LOOM-EXPECTED-HEAD-MISMATCH pr=<N> expected=<sha> actual=<sha\|unknown>`. Nothing was merged or written. | Not a failure comment. The caller's evaluation describes another tree: re-run the evaluation on the current head (a targeted Champion ends its step with `outcome=head-moved`). Never retry the same `--expected-head`. |
| `10` | yes | *(Champion Step 3 only)* `loom-daemon champion-hold classify` did not answer `state=clear`: a Champion hold, another actor's `loom:blocked` park, a verdict contradiction, a PR whose base is a Loom stack branch (`feature/issue-N` or `feature/harness-ops-N`), open parent or not (#12761), or an unreadable state (#11932). `merge-pr.sh` never ran. | No "Merge Failed"; skip silently. A park is someone's decision, not a failure. |
| *(none)* | unknown | The caller was killed before the script could exit — the only outcome that leaves no forge-visible trace (#9096). | Re-read the PR; see "No exit code at all". |

Retryable outcomes never post a failure comment and never count as errors.

## Exit 3 — a foreign push raced the merge (#5579)

`merge-pr.sh` passes the head SHA it read to the forge's merge API as an
optimistic-concurrency precondition. When the branch has moved on, the forge
refuses and the script exits 3 rather than 1: the PR is still Judge-approved,
its diff just moved out from under the attempt. Most commonly a session pushed
new commits to an open, `loom:pr`-labeled branch while Champion was running.

**Diagnostic output.** The script logs to stderr both the stale SHA (the one it
gated the merge on) and the current head SHA, so it is easy to see which
commits raced in. These appear in the `merge-pr.sh` output and the caller's run
log. They are deliberately **not** posted as a PR comment: an exit-3 re-queue is
an ordinary operational event, and commenting on every occurrence would be
noise on a race condition that resolves itself.

## Exit 4 — retired (#12063)

Exit 4 meant "the #8248 required-check freshness guard blocked the merge and
`--redate-stale-checks` pushed a tree-identical no-op commit (#8508) so CI
re-tested the current base". #12063 slice 1 deleted the guard, the re-date
remedy, its budget and sync hand-off, and the #10444 CI-run conclusion gate:
whether the required checks at the approved head are green is GitHub's
decision (the ruleset's required contexts), and a PR whose head and green
checks are unchanged is no longer re-dated because `main` moved. The accepted
cost is the occasional semantic conflict, caught by CI on `main` and reverted.

`merge-pr.sh` never exits 4 now, and callers may keep treating 4 as a
re-queue. `--redate-stale-checks` and the `stale-checks`, `ci-result` and
`redate-checks` verbs are removed outright, with no deprecated stand-in: a
Champion prompt or `merge-pr.sh` that still uses them refuses the merge
(fails closed) until its repo resyncs `.loom/`.
`loom-daemon merge-pr redate-report` and the `loom.merge.redate_*` gauges
remain for the #10888 before/after measurement.

## Exit 5 — a required check is pending or red (#12063)

`merge-pr.sh` makes one merge call and waits for nothing. Before #12063 slice 2,
`--auto` polled the head's check-runs for up to `LOOM_AUTO_MERGE_TIMEOUT`
(#8410, #8896), and a stale-mergeable pre-read and a branch self-sync sat in
front of the call. All of that is deleted: GitHub's ruleset decides whether the
required checks at the approved head are acceptable, and `--auto` and
`LOOM_AUTO_MERGE_*` are accepted and ignored (`--auto` prints a one-line
warning).

**Kept: the required-context conclusion gate (#10688).** `_check_required_checks`
(`loom-daemon merge-pr required-checks`) still runs once before the call. A
bypass-capable (admin) token walks through the ruleset's required checks
(a ruleset-required-check bypass, see #10688), so the script itself refuses (exit 1) a red required
context and holds (exit 5) a missing or pending one;
`--allow-red-required <context>` overrides exactly the named contexts and
records an audit comment. It is GitHub-only and fails open on a daemon that
predates the verb.

When the forge refuses the call because a required status check is pending or
red, the script exits **5**: nothing merged, the head did not move, the verdict
stands, so the next pass simply retries. It is the same shape as exit 3 and
must never reach Champion's "Merge Failed" path. A repo that hits it every pass
has a required check that does not finish before Champion looks; fix the check
or the required set, not this script.

What exit 5 deliberately is **not**:

- **Not a head move.** Nothing pushed, so exit 3's #5686 caveat does not apply.
- **Not a bypass.** The forge refused; nothing was merged.
- **Not a wait.** The script never polls; a caller that wants to wait re-runs it.

## Exit 7 — the merge-queue step withheld the direct merge (#10256, #10628)

Champion's Step 3 runs `loom-daemon forge merge-queue step <PR> --approved-sha
<head>` before `merge-pr.sh`. Only a first **stdout** line of
`LOOM-MERGE-QUEUE-DIRECT` with exit 0 lets `merge-pr.sh` run. Every other result
sets `MERGE_RC=7`. Nothing was merged, the head did not move, and the verdict
stands. The two kinds of 7 are handled differently:

| `step`'s first stdout line | Meaning | Champion's handling |
|---|---|---|
| `LOOM-MERGE-QUEUE-QUEUED` / `-DROPPED` / `-HANDED-OFF` / `-MERGED` | The queue protocol is working | Silent, like `merge-pr.sh`'s 3-7: the result is logged and the PR is re-queued |
| anything else: `-UNDETERMINED`, `-REFUSED`, `-DIRECT` with rc≠0, empty output, an invalid `champion.mergeMode`, an old binary that cannot prove direct mode, `command not found` | **A stall.** In a direct-mode repo this stops *every* merge on the host | Logs `CHAMPION-MERGE-QUEUE-STALL pr=N: <stdout lines> <stderr first line> (rc=R)` and posts one PR notice per head (`<!-- champion:merge-queue-stall pr=N sha=HEAD -->`, the same dedup shape as `champion:merge-outcome-unknown`). Then re-queues; not an error |

`step`'s stderr is captured, never discarded, so the cause is named. Before
#10628, an old binary showed up only as ` (rc=2)` in the transcript.

### Old daemons: direct merge only on proven direct mode

Role prompts reach a host through `resync-installed.sh` / defaults sync
separately from the `loom-daemon` binary. A host can therefore run the B3
prompt on a binary that has no `step` verb. Two rules pull against each other
here:

- **Judge P1 on #10585.** A daemon from v0.19.791 (B2) onward has no `step`
  verb but *does* honor `champion.mergeMode=queue`. So "unrecognized subcommand"
  alone is never permission to merge directly. That would bypass the queue
  authorization protocol.
- **Fleet liveness.** Blocking every direct-mode merge on every un-upgraded host
  is an outage, even when it is surfaced.

Step 3 resolves this with an independent proof of direct mode. Only the anchored
clap error counts (exit 2, empty stdout, stderr first line exactly as shown):

| stderr first line | Proof attempted | Result |
|---|---|---|
| `error: unrecognized subcommand 'step'` (v0.19.761+, before B3) | `loom-daemon forge merge-queue mode`, which is the same binary's own env > tiered config > default resolver. It must exit 0 and print `merge-queue: mode=direct source=…` | direct: logs `LOOM-MERGE-QUEUE-COMPAT …` and runs the pre-#10256 `merge-pr.sh` call. queue / invalid / failed: stall |
| `error: unrecognized subcommand 'merge-queue'` (before v0.19.761, e.g. 0.19.743) | None needed. The binary predates `champion.mergeMode`, so it cannot run the queue protocol. Its only merge path is direct | logs `LOOM-MERGE-QUEUE-COMPAT …` and runs the direct merge |

The mode is deliberately **not** read with `jq` from `.loom/config.json`.
`champion.mergeMode` is resolved across four config tiers (private defaults,
`.loom/config.json`, `.loom-project/project.json`, `.loom-local/local.json`),
so a shell mirror would miss a host-tier `queue`. Asking the binary's own
resolver is the only proof that matches what the daemon will actually do.

Accepted edge: a `queue` setting (env or config) on a host whose binary has no
`merge-queue` verb still merges directly. That binary has no queue protocol to
bypass. It cannot hand off, authorize, or reconcile, so a direct merge is the
only thing it can do, and it is the merge this host performed before B3. Queue
execution is compiled on (`QUEUE_EXECUTION_ENABLED=true`, #12323) but only a repo
that sets `champion.mergeMode=queue` reaches it. Before opting a repo in, set a
fleet `loom-daemon` version floor that includes `step`, and then this row can
become a stall.

Regression: `defaults/scripts/tests/test-champion-merge-queue-step-no-fallthrough.sh`
extracts the shipped Step 3 fence and runs every row above against stubs.

## Exit 7 from `merge-pr.sh` — a sequencing hold (#11330)

`loom:sequenced` (#9378) is in the verdict-contradiction guard's blocking set,
so a PR carrying it beside `loom:pr` is refused. That refusal used to be exit 1,
which a caller could not tell from a Judge rejection without grepping the text.
When `loom:sequenced` is the ONLY blocker, `merge-pr.sh` now exits 7 and prints
`LOOM-SEQUENCED-HOLD pr=<N> after=<M>`: the order resolves on its own when the
predecessor `<M>` lands. `after` comes from the PR's trusted `loom:sequence`
marker, best-effort (`after=unknown` when unreadable); the hold itself is still
decided by the label alone. Any second blocker (`loom:changes-requested`,
`loom:operator`, …) keeps exit 1, because the PR stays blocked after the
predecessor lands.

A sequencing hold has no cap of its own (the
`sequence-eval` pass owns its release). It is opt-in on the daemon side —
`merge-pr.sh` sets `LOOM_SEQUENCED_HOLD_REPO` — so an older `loom-daemon`
ignores it and answers exit 1 as before, and an older `merge-pr.sh` never sees
a 7. Champion already re-queues every 7 silently.

## No exit code at all — the caller was killed (#9096)

This is the fifth outcome, and the only one that is not an exit code: the
merge call produced **no classifiable result whatsoever** because the process
running it was terminated. Until #12063 slice 2 the usual cause was
`merge-pr.sh --auto`'s settle-wait (default 600s) racing a Bash tool call capped
at 600s; the script now waits on nothing and returns in seconds, so the race is
gone and only a genuinely hung call (a stuck forge request, a killed host) can
still produce it.

What that leaves on the forge is worse than any of exits 3-7: Step 2 has
already posted "Proceeding with merge…", and then there is nothing. No merge,
no failure, no label change, no comment — indistinguishable from a dead host.
That is the 2026-09-26 incident on a private fleet repo: a "Proceeding with
squash merge…" comment at 14:34:43Z, then silence until a human merged by hand
at 15:02:11Z — the same timeline #9091 traced to the unbounded zero-row
re-poll. #9091 removed the common *cause*; it did not make the outcome
visible, which is this section.

### The remaining fix: make the unclassified case visible

(The first fix of #9096, pinning `LOOM_AUTO_MERGE_TIMEOUT` strictly under the
tool timeout so exit 5 wins the race, went with the wait it bounded, #12063.)

1. **Make the unclassified case visible.** A sentinel line
   (`CHAMPION-MERGE-OUTCOME pr=… rc=…`) is the last statement of Step 3's
   block. A killed call never reaches it, so its **absence** is the caller's
   only evidence that no `MERGE_RC` was ever evaluated. On absence, Champion
   re-reads the PR state and — if it is not merged — posts a
   **"Merge Outcome Unknown"** notice.

### The recipe

Champion's prompt states the rule; this is the exact shape it describes, to be
run when Step 3's output ends without the sentinel. The `exit 0`s below are
written for a single-PR invocation — in a batch loop they are `continue`, the
same convention Step 2's pre-merge comment uses. Afterwards `loom:pr` stays on
the PR and the tick records an *unknown outcome*, never an error.

```bash
# Re-read first: a killed call may still have merged and lost only its report.
# Plain `gh`, NOT "$GH_READ" — a cached read could mask your own merge.
PR_JSON=$(gh pr view "$PR_NUMBER" --json state,headRefOid 2>/dev/null || echo '{}')
STATE=$(printf '%s' "$PR_JSON" | jq -r '.state // "UNREADABLE"')
HEAD_SHA=$(printf '%s' "$PR_JSON" | jq -r '.headRefOid // "unknown"')
MARKER="<!-- champion:merge-outcome-unknown pr=$PR_NUMBER sha=$HEAD_SHA -->"

case "$STATE" in
  MERGED)
    echo "PR #$PR_NUMBER merged; only the report was lost — continue to Step 4"
    exit 0 ;;
  OPEN)       STATE_LINE="As of this comment the PR is **not merged** and is still Judge-approved" ;;
  *)          STATE_LINE="The re-read of this PR's state also failed, so even whether it merged is unconfirmed" ;;
esac

# Idempotency, same shape as every other Champion notice (champion:ac-hold,
# champion:merge-risk-hold, …): one notice per PR per head. A head that moves
# is a new episode and gets a fresh notice.
if gh pr view "$PR_NUMBER" --json comments \
     --jq '.comments[].body' 2>/dev/null | grep -qF "$MARKER"; then
  echo "PR #$PR_NUMBER already carries an unknown-outcome notice for $HEAD_SHA"
  exit 0
fi

gh pr comment "$PR_NUMBER" --body "**Champion: Merge Outcome Unknown**

Champion started an auto-merge for this PR (see \`Proceeding with merge...\` above) and the call was cut off before reporting anything — its worker timed out or was killed.

This is **not** a merge failure: no error was returned, because no result was returned at all. $STATE_LINE, and a later Champion pass re-evaluates and retries it — no human action is required unless this recurs on the same PR.

---
*Automated by Champion role*
$MARKER"
```

The three-way `case` matters: the notice's value is that every sentence in it
is something Champion actually knows. On an `OPEN` re-read it can say the PR is
not merged; on an unreadable one it cannot, and saying so is still strictly
better than silence. Never collapse the two into the `OPEN` wording — that
turns an honest state report into the same unverified assertion the "Merge
Failed" comment is being avoided for.

### Why the notice is not the "Merge Failed" comment

The distinction is load-bearing in both directions, and it is the rule conflict
this section exists to settle:

- **It is not a failure.** "Merge Failed" asserts an error was returned and
  ends with "a human will need to investigate and merge manually." Here no
  error was returned because *no result was returned at all*, and no human
  action is required — the PR is still Judge-approved and a later pass retries
  it. Posting the failure wording would manufacture an incident out of a
  timeout and park a mergeable PR on a human.
- **It is also not covered by the exits-3-7 silence rule.** Those runs stay
  silent on the forge because they *reported themselves*: the caller knows the
  outcome, records it, and re-queues; commenting on a self-resolving race
  would be noise (see exit 3 above). A killed call reports nothing, so silence
  there is not "an ordinary operational event went unremarked" but "Champion
  announced a merge and vanished." **The silence rule is conditioned on having
  an outcome to be silent about**, and must never be generalised to cover its
  absence — nor may the notice ever be extended to fire on exits 3-7, which
  stay exactly as silent as they are today.

The notice is therefore worded as a *state report*, not a verdict: what
Champion started, that the result is unknown, that the PR is not merged as of
that comment, that it re-queues automatically, and that a human should look
only if it recurs on the same PR. Re-reading the PR first keeps it honest —
a killed call can still have merged and lost only its report, in which case
there is nothing to announce and Step 4 proceeds normally.

### Sweep's own merge callsites take the notice's absence, not the notice (#9395)

`/loom:sweep` reaches this script from `sweep-wave-lifecycle.md` step 7 and
`sweep-mode-c-lifecycle.md` C2. They pin nothing since #12063 (the script waits
on nothing, so the default tool timeout suffices), and they do **not** use the
"Merge Outcome Unknown" notice, for two reasons specific to the sweep:

1. **Nothing is on the forge to be left dangling.** A sweep's Merge phase posts
   nothing before merging, so a killed call leaves the PR exactly as Judge left
   it: `loom:pr`, approved, untouched.
2. **The sweep has durable local state Champion does not.** Its checkpoint is
   written only after a phase completes, so a killed merge leaves `judge-done`
   on disk and the next pass's "Mid-phase-death recovery"
   (`sweep-wave-lifecycle.md`, #3683) re-verifies forge state and completes only
   the missing steps.

If a sweep's Merge phase ever posts a pre-merge comment, or deletes the
checkpoint before `merge-pr.sh` returns, reason 1 or 2 stops holding and the
sentinel becomes required there too.

## Merge-ancestry detection trap (applies to all of them)

If you need to verify by hand whether a re-queued PR's commits actually landed
or were silently stranded, `git merge-base --is-ancestor <commit> origin/main`
is **not reliable evidence for a squashed merge**: a squash merge produces a
brand-new commit SHA on `main` that is not a git-ancestry descendant of any
commit on the original PR branch, regardless of whether that commit's content
made it into the squash. Loom's default is now merge commit (#9105), under
which the PR branch's commits ARE ancestors of `main` — there the ancestry
check works as expected. For a squashed PR (or on any repo configured
squash-only), there is no cheap ancestry check for "squashed-and-landed" vs.
"stranded" — verification requires diffing the actual file content on `main`
against the branch or commit in question.
